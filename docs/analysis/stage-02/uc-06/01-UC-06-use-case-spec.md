> **范围：** 本 UC 只处理“有权审核的管理员对待审核/待补充的认领申请核验证据、作出决定（批准/驳回/要求补证/记录争议）、批准时授予目标 Scholar 的对象级管理授权、并把决定与授权留痕”的过程。申请人提交与本人查询属 UC-05（直接前驱，其 E6/M19 产生本 UC 输入的申请）；已授权 Scholar 档案维护属 UC-07；成果归属确认/纠错属 UC-08/UC-10；后台待办与审计查询属 UC-17。本 UC **不创建** Scholar、**不创建第二个 UserProfile**、**不创建/确认任何 Authorship**、**不改写 Scholar 档案字段**、**不删除成果**、**不转移既有授权**。

## 1. 参与者

| 类型 | 参与者 | 说明 |
|---|---|---|
| 主要参与者 | 有权审核的管理员（登录、具备审核认领的权限） | 打开待审核/待补充申请、查看证据、作出决定、查询本人作出的决定与审计依据 |
| 次要参与者（只读） | 登录申请人（申请所属 User） | 仅能读取本人申请的状态与决定；该读取路径属 UC-05 的 E9–E11，本 UC 只把决定记录为“本人可读的投影”，不重新实现查询 |

> SRS §2.2 把“管理员按具体权限管理来源、核验和审核”作为业务角色；§8 权限表对“本人认领申请/查看私有结果”的管理员一列写“审核权限”；FR14 明确“不同管理员仍遵守对应权限”。
> **不引入审核员等级、审批链或角色继承**：基线只区分“是否具备该审核权限”。“受控待办/审核队列”的载体属 FR14/UC-17（C-05），本 UC 只把申请置为相应状态并留痕。

## 2. 目标

有权审核的管理员在服务端授权与审计约束下，对一条待审核/待补充的 Scholar 认领申请给出**有理由、可追溯**的决定：批准（仅无冲突、仅授予目标 Scholar/门户的对象级管理权）、驳回、要求补证、记录争议；并保证竞争认领保留原授权、不自动转移，决定与授权均留痕且可被查询。

## 3. 触发事件

有权审核的管理员在其审核入口打开一条状态为**待审核**或**待补充**的认领申请，并作出决定；或查询某申请已作出的决定与审计依据。

## 4. 前置条件

1. 请求者已登录且账号可用，并具备审核认领的权限；身份、账号状态与权限由服务端每次校验（FR14；NF03；SRS §8“每次操作的权限判断在服务端执行”）。
2. 存在一条**由 UC-05 产生**的 `ClaimApplication`，状态为 `待审核` 或 `待补充`，且申请人、目标 Scholar、证据引用齐备（FR05；`DGM-STATE-02`）。
3. 该申请的证明材料为私有：仅申请人本人与有权审核者可见（BR-IMP-11；NF06；AC-IMPL-NF06-01）。
4. 目标是平台**已收录**的 Scholar 档案（可无账号）；本 UC 不创建 Scholar（FR05；SRS §12）。
5. 审核不依赖未定义的角色层级、SLA 与申诉程序；这些未冻结项不得在模型中伪造（D-06；SPEC ID-12）。

## 5. 成功与失败后置条件

### 5.1 批准成功（无未决冲突且授权写入成功）

1. **恰好新增一条** `ScholarAuthorization`：被授权主体=该申请的申请人 User，目标=该申请的目标 Scholar，范围为**仅该目标门户/档案的对象级管理权**（AC-IMPL-FR05-02；BR-IMP-05；SPEC ID-07）。
2. 申请状态=**通过**，记录决定理由与决定时间；申请人的本人查询可读到该状态与理由（AC-IMPL-FR05-02；读取路径属 UC-05）。
3. **未**创建 Scholar、**未**创建第二个 UserProfile、**未**合并主页、**未**改写 Scholar 档案字段、**未**创建或确认任何 `Authorship`、**未**删除任何成果（FR05；AC-IMPL-FR05-04；SPEC ID-07）。
4. 审计记录含：决定（批准）、操作者、对象（申请/目标 Scholar/新授权）、时间、前后值（申请状态、授权有无）、理由（FR14“关键批准…记录操作者/对象/时间/前后值/原因”；BR-IMP-10；SPEC §3 INV-10）。
5. 既有授权未被转移或撤销；批准分支只在读取到“无未决冲突”时执行（AC-IMPL-FR05-03；BR-IMP-05）。

### 5.2 驳回

1. 申请状态=**驳回**，记录理由与时间；申请人可查询。
2. **不撤销、不改动、不转移**既有授权；不删除 Scholar、主页或成果（AC-IMPL-FR05-03；`DGM-ACTIVITY-01`“已驳回 不撤销原授权”）。
3. 审计留痕（决定/操作者/对象/时间/前后值/理由）。

### 5.3 要求补证

1. 申请状态=**待补充**，记录缺失项/需补材料与理由；申请人可查询（AC-IMPL-FR05-01“标待补充并说明缺失”）。
2. 既有授权不变；不产生授权；不删除任何材料或成果。
3. 审计留痕。
4. 本人补证重提属 UC-05 的提交侧；本 UC 的补证复核（A4）在材料齐备时把状态放行回 `待审核`，仍缺项时保持 `待补充`。

### 5.4 记录争议

1. 申请状态=**争议**，记录冲突事实与理由；申请人可查询（AC-IMPL-FR05-03）。
2. **原授权保留**：不撤销、不修改、不转移；不创建新授权；不因争议自动使门户变为“未认领”（AC-IMPL-FR05-03；BR-IMP-05；SRS §6.3）。
3. 争议属于“受控待办”的入口事实；待办列表/结案队列的载体属 FR14/UC-17（C-05）。
4. 审计留痕。

### 5.5 失败与拒绝（无业务写入）

1. 未登录、账号停用或无审核权限：拒绝，无任何写入（NF03；AC-IMPL-NF03-01；SRS §8）。
2. 申请已被他人决定或版本已变化：拒绝本次决定并返回当前状态，不覆盖已有决定（`DGM-STATE-02`“过期审核/授权失败不改变原状态”）。
3. 理由缺失/不完整：拒绝该决定，状态不变（`DGM-STATE-02` 守卫“有权且理由完整”）。
4. 授权写入失败：申请保持原状态（待审核/待补充），**不虚报通过**；记录失败与前后值（`DGM-STATE-02`“审核/授权提交[过期或授予失败]/拒绝决定，保持原状态”；`DGM-ACTIVITY-01`“授权失败 保持先前状态”）。
5. 审计留痕失败：决定不得报告为**已生效**，不得留下无审计的生效决定（SPEC §3 INV-10；BR-IMP-10；分析推导）。
6. 拒绝、失败、争议、待补充、通过五类结果在审核视图与申请人视图中可区分，不共用同一文案（NF01 三态可分；分析推导）。

### 5.6 决定查询

1. 有审核权限的管理员可读取自己作出的决定与审计依据（决定、理由、操作者、时间、前后值）（FR14；AC-IMPL-FR14-02 边界）。
2. 查询只读：不改变申请状态、不产生或修改授权。
3. 无审核权限者查询：拒绝（NF03；AC-IMPL-NF03-01）。
4. 申请人对本人结果的读取属 UC-05 E9–E11（只读）；本 UC 通过“决定被记录为本人可读投影”保证其可读性（AC-IMPL-FR05-02）。

## 6. 基本事件流

| 步骤 | 事件 | 需求来源 |
|---:|---|---|
| E1 | 审核者在其审核入口打开一条待审核/待补充的认领申请，请求审核上下文。 | FR05；FR14“认领审核统一入口”；SRS §8 |
| E2 | 系统在服务端校验审核者身份、账号状态与审核认领的权限。 | FR14；NF03；AC-IMPL-NF03-01；SRS §8 |
| E3 | 系统读取申请当前状态、申请人/目标 Scholar/证据引用、版本与最近理由。 | FR05；`DGM-STATE-02`“审核必须校验当前版本” |
| E4 | 审核者查看该申请的私有证明材料，核对申请人与目标 Scholar 的对应关系。 | FR05“可核验证据”；BR-IMP-11；NF06；AC-IMPL-NF06-01 |
| E5 | 系统读取目标 Scholar 当前有效授权，判定是否存在未决冲突（只读，不改动）。 | AC-IMPL-FR05-02/03；BR-IMP-05；SPEC ID-12 |
| E6 | 审核者选择决定（批准/驳回/要求补证/记录争议）并填写理由。 | FR05 状态集；`DGM-STATE-02`“有权且理由完整”；`DGM-ACTIVITY-01`“记录批准或驳回及证据理由” |
| E7 | 系统复核守卫：审核权限仍有效、申请状态未变、理由完整、批准时无未决冲突。 | `DGM-STATE-02`“事件 [守卫]；审核必须校验当前版本和权限”；AC-IMPL-FR05-02/03 |
| E8 | [批准且无冲突] 系统创建仅对目标 Scholar/门户生效的对象级管理授权（被授权主体=申请人）。 | AC-IMPL-FR05-02；BR-IMP-05；SPEC ID-07 |
| E9 | 系统记录申请状态与理由（通过/驳回/待补充/争议），形成本人可读的决定投影。 | FR05 状态集；AC-IMPL-FR05-01/02；`DGM-STATE-02` |
| E10 | 系统写入审计：决定、操作者、对象、时间、前后值、理由。 | FR14；BR-IMP-10；SPEC §3 INV-10 |
| E11 | 系统返回决定与生效结果（授权已生效 / 授权失败保持原状态 / 争议待人工结论）。 | AC-IMPL-FR05-02/03；`DGM-STATE-02` |
| E12 | 审核者查询该申请已作出的决定与审计依据（只读）。 | FR14；AC-IMPL-FR14-02（边界）；AC-IMPL-FR05-02 |

## 7. 备选/异常流

| 编号 | 条件 | 系统行为 | 依据 | 说明 |
|---|---|---|---|---|
| A1 | 未登录、账号停用或无审核权限 | 拒绝，无任何写入，不返回申请与证据内容。 | NF03；AC-IMPL-NF03-01；FR14 | 前端入口隐藏不代替服务端拒绝 |
| A2 | 申请已被他人决定或版本已变化 | 拒绝本次决定并返回当前状态；不覆盖已有决定。 | `DGM-STATE-02` 过期审核守卫 | 与 A1、A8 的结果分开显示 |
| A3 | 审核者要求补证 | 状态=待补充，记录缺失项/需补材料与理由；不创建授权；原授权不变。 | AC-IMPL-FR05-01；`DGM-ACTIVITY-01`“需要补证→待补充并说明原因” | 阈值/证据最低集合未冻结（C-02） |
| A4 | 待补充申请的补证复核 | A4a 复核齐备→状态回待审核并记录复核理由；A4b 仍缺项→保持待补充并更新缺失项。均不产生授权。 | `DGM-STATE-02`“本人重提[校验通过]”；AC-IMPL-FR05-01 | 本人重提属 UC-05；校验口径未冻结（C-07） |
| A5 | 拟批准但存在未决冲突（门户已有他人有效授权或身份冲突未决），或审核者直接记录争议 | **不得批准**：状态=争议，理由=冲突事实；**原授权保留**、不转移、不撤销；不创建授权。 | AC-IMPL-FR05-03；BR-IMP-05；SPEC ID-12；SRS §6.3；`DGM-ACTIVITY-01`“进入争议 保留原管理授权” | 争议结案与授权转移/申诉程序待评审（C-05） |
| A6 | 授权写入失败 | 申请保持原状态，记录失败原因与前后值；不虚报通过，不返回“已通过”。 | `DGM-STATE-02`；`DGM-ACTIVITY-01`“授权失败 保持先前状态”；SPEC INV-10 | 重试程序未定义（C-12） |
| A7 | 审核者驳回 | 状态=驳回，记录理由；不撤销、不改动原授权；不删除档案/成果。 | AC-IMPL-FR05-03；`DGM-STATE-02`“驳回[有权且理由完整]”；`DGM-ACTIVITY-01` | — |
| A8 | 理由缺失或不完整 | 拒绝该决定并要求填写理由；状态不变。 | `DGM-STATE-02`“理由完整”守卫；FR14“记录…原因” | 与 A1/A2 分开 |
| A9 | 审计留痕失败 | 决定不得报告为已生效；不留下无审计的生效决定；明确失败。 | SPEC §3 INV-10；BR-IMP-10 | 回滚机制属实现阶段；本 UC 只约束“不报告生效” |

## 8. 业务规则

| 规则 | 内容 | 来源 |
|---|---|---|
| BR-UC06-01 | 审核主体必须是具备审核认领权限的登录管理员；身份、账号状态与权限每次在服务端校验。 | FR14；NF03；SRS §8 |
| BR-UC06-02 | 审核只作用于 `待审核`/`待补充` 申请；已被决定或版本已变化的申请不覆盖、不重写。 | `DGM-STATE-02`；AC-IMPL-FR05-02 |
| BR-UC06-03 | 决定集合限于 `通过/驳回/待补充/争议`，理由完整是守卫；缺失理由不得改变状态。 | FR05 状态集；`DGM-STATE-02`；FR14 |
| BR-UC06-04 | 批准仅在**无未决冲突**时成立；读取到他人有效授权或未决身份冲突时不得批准，只能记录争议。 | AC-IMPL-FR05-02/03；BR-IMP-05 |
| BR-UC06-05 | 批准只授予被批准申请人对**目标 Scholar/门户**的对象级管理权；不产生第二个 UserProfile、不创建 Scholar、不改写档案字段。 | AC-IMPL-FR05-02/04；SPEC ID-07；SRS §12 |
| BR-UC06-06 | 竞争认领保留原授权：不撤销、不修改、不自动转移；争议进入受控待办的入口事实；转移与申诉程序待评审。 | AC-IMPL-FR05-03；BR-IMP-05；SPEC ID-12；SRS §6.3 |
| BR-UC06-07 | 批准不等于本人确认：不自动确认任何 Authorship（既不确认全部，也不因批准升级其他候选关系）。 | FR05；FR15；AC-IMPL-FR15-03/06；SPEC ID-07 |
| BR-UC06-08 | 审核决定必须留痕：决定、操作者、对象（申请/目标 Scholar/授权）、时间、前后值、理由。 | FR14；BR-IMP-10；SPEC §3 INV-10 |
| BR-UC06-09 | 审核材料私有：仅申请人本人与有权审核者可见；审核视图不向普通用户回显材料原文。 | BR-IMP-11；NF03；NF06；AC-IMPL-NF06-01 |
| BR-UC06-10 | 失败不虚报：无权限、状态过期、理由缺失、授权失败、审计失败分别返回明确结果，均不得写成“已通过”。 | `DGM-STATE-02`；INV-10；NF01（分析推导） |
| BR-UC06-11 | 决定必须对申请人**只读**可查（状态+理由）；申请人读取路径属 UC-05，本 UC 只保证记录可读。 | AC-IMPL-FR05-02；UC-05 E9–E11 |
| BR-UC06-12 | 不引入审核员等级、审批链、SLA 与申诉程序；这些未冻结项不写入模型。 | SRS 无定义；D-06；SPEC ID-12 |

## 9. 关联状态

> 状态集按 FR05 与 `DGM-STATE-02` 使用 `待审核/待补充/通过/驳回/争议`；`DGM-STATE-02` 与 SPEC §3 写作 `已通过/已驳回`，本包按需求表述视二者同义（C-10）。本 UC 不新建状态机，只引用既有图并界定哪些迁移属本 UC。

| 迁移 | 触发者 | 守卫 | 归属 |
|---|---|---|---|
| `待审核 → 待补充` | 有权审核者 | 有权且理由完整（缺失项说明） | 本 UC（A3/E9） |
| `待审核 → 通过` | 有权审核者 | 无冲突 ∧ 授权写入成功 | 本 UC（E8–E10） |
| `待审核 → 驳回` | 有权审核者 | 有权且理由完整 | 本 UC（A7） |
| `待审核 → 争议` | 有权审核者 | 记录争议或拟批准时发现未决冲突 | 本 UC（A5） |
| `待审核 → 待审核`（无迁移） | — | 授权失败或过期：拒绝决定，保持原状态 | 本 UC（A2/A6） |
| `待补充 → 待审核` | 有权审核者（本人已重提） | 复核补证齐备 | 本 UC（A4a，口径待 C-07） |
| `待补充 → 待补充`（无迁移） | 有权审核者 | 复核仍缺项 | 本 UC（A4b） |
| `争议 → 待审核 / 待补充 / 驳回` | 人工结案 | `DGM-STATE-02` 有边；结案条件与授权解封/转移、申诉程序待评审 | **不在本 UC 展开**（C-05） |
| `[*] → 待审核 / 待补充` | 申请人 | 提交侧校验 | UC-05（E5–E7） |
| 本人查询（任意状态） | 申请人 | 仅本人 | UC-05（E9–E11，只读） |

`DGM-STATE-02` 未定义 `待补充 → 驳回/争议` 的边；本 UC 不擅自新增，待补充申请先经 A4 放行回 `待审核` 再作决定，差异登记 C-06。

## 11. 待确认

1. **C-01**：审核权限的具体划分（是否按机构/对象/申请类型）——SRS §8 只写“审核权限”，FR14 只要求“遵守对应权限”；本 UC 不引入等级/审批链。
2. **C-02**：必要证据的最低集合与“可核验”判定口径（沿用 UC-05 B-02/D-06）——直接影响“批准”与“要求补证”的判定。
3. **C-03**：审核 SLA/超时兜底（D-06）——本 UC 不写 SLA。
4. **C-04**：同一 Scholar 是否允许并列多个管理者（SPEC ID-12 待评审）——影响批准守卫与 `ScholarAuthorization→Scholar` 多重性。
5. **C-05**：争议“受控待办”的载体、结案程序、授权解封/转移与申诉程序（SPEC ID-12；UC-05 B-06）——本 UC 只记录争议并保留原授权。
6. **C-06**：`待补充` 申请能否被直接驳回/记争议——`DGM-STATE-02` 只定义 `待补充→待审核`；本 UC 不新增边。
7. **C-07**：补证重提的校验口径与放行归属（UC-05 B-04）——本 UC 只表达“复核齐备后放行”，不定义阈值。
8. **C-08**：审计类命名与拆分（`ReviewEvidence`/`AuditEvidence`/`Evidence`；D-13、UC-05 B-05）。
9. **C-09**：控制类命名与拆分（`ClaimCoordinator`/`ClaimReviewCoordinator`/`ClaimCtl`；B-09/D-11）。
10. **C-10**：状态名口径（FR05 `通过/驳回` vs SPEC §3/`DGM-STATE-02` `已通过/已驳回`；UC-05 B-11）。
11. **C-11**：决定/补证的通知渠道与内容（SRS 未定义；UC-05 B-07）——本 UC 只保证“可查询”。
12. **C-12**：授权失败后的重试/再提交程序与审计失败时的回滚机制（`DGM-STATE-02` 只写保持原状态）。
