# UC-19 分析类职责、属性、关系与分析机制

**版本：** V1.0（2026-10-21）
**方法：** 教材 §5.5.1 职责、§5.5.2 属性、§5.5.3 关系、§5.5.4 分析机制。
**范围：** 只定义 UC-19 能够证实的部分；跨用例统一关系不在此擅自补齐。

## 1. 定义原则

1. “做（Do）”型职责说明对象能执行/协调什么；“知道（Know）”型职责说明对象必须知道/提供什么。
2. 属性只写业务信息，不写数据库字段、主键类型、索引或 API 参数；检查点间隔、批次大小、观察版本的实现形式不在分析层定义。
3. 关系只写有消息或正式业务约束支持的；属主 UC 已定义的关系（`WorkEntity–WorkVersion`、`SourceDefinition–SourceRecord`）沿用不重定义。
4. 控制类没有长期业务属性；来源域守卫、分类、冲突判定、重检与计数核对都是单次用例的分析状态。
5. 检查点间隔与批次大小（B-01）、退化比较规则（B-02）、回溯范围口径（B-03）、冲突处置责任与时限（B-04）、失效事件对公开资格的影响（B-05）未冻结，一律标 `待确认`，不写成类定义里的既定规则。

## 13. 三种“版本”语义（本 UC 的关键区分）

| 术语 | 载体 | 语义 | 谁写 | 混用后果 |
|---|---|---|---|---|
| 来源侧记录版本 | `SourceRecord.observedRevision`（及 `arrivalEvents[].observedRevision`） | 该逻辑出处在本轮被观察到的**来源侧版本标识**，用于与“上次版本”比较 | 本 UC（观察追加） | 把成果版本当来源版本会导致“同一记录每次都被判变更”或“真实变更被判未变” |
| 本轮基线 | `IncrementalChangeSet.baselineRef`＋`baselineIsFallback` | 本轮比较的起点（上次检查点/观察版本集合；无基线时为回溯范围） | 本 UC（逐轮记录） | 把基线当成果版本会让“复跑幂等”失去依据（A7） |
| 成果发布形态 | `WorkVersion` | 预印本/修订/正式发表等**有明示证据**的版本关系，属于一个 `WorkEntity` | **UC-09**（DD-08）；本 UC 只读 | 由本 UC 建立版本会越过 UC-09 规则，并可能使实体被双计或静默压缩（SPEC §5.5） |

> FR10 的“上次版本”指**来源侧记录版本**，不是 `WorkVersion`；本 UC 因此不建立、不修改版本关系，只在 E13 记录明示版本证据并交治理（M59–M61）。
