## 1. 问题

当前 `SourceAdminService.setEnabled(actor, sourceId, enabled, reason)` 用一个布尔同时表达两种
互不相同的业务含义：

1. **暂停新增／更新任务**：不再从该来源采集新数据。历史已获展示许可的成果应当继续可读。
2. **撤销展示许可**：该来源的数据不再允许公开展示，依赖它的成果必须下线。

代码可见的行为是：`enabled=false` 时，除了置位来源配置，还会把「唯一来源是该来源」的
`PUBLIC` 成果批量改成 `RESTRICTED`（`SourceAdminService` 第 162–180 行，
`AchievementMapper.findExclusivelyFromSource`），随后推进权威公开水位并发出收紧事件。
`enabled=true` 时没有任何反向动作。

这与现行 SRS「来源停用后既有公开成果仍可读」直接冲突：**同一个开关，做的是撤权的事**。

## 2. 三处具体风险（均为代码可见，未实测）

### 2.1 语义混用导致「停采集 = 下线历史」

一次常规故障暂停（例如上游限流、维护窗口）会让该来源独占的公开成果整体消失，
检索、统计、合作网络与旧链接同时受影响。操作者想表达的是「先别抓了」，
系统执行的是「这些成果不再公开」。

### 2.2 5001 条及以上时只收紧前 5000 条

`findExclusivelyFromSource(sourceId, TIGHTEN_BATCH_LIMIT)` 带 `LIMIT 5000`，
方法内没有继续分页，也没有把「还有剩余」这件事返回给调用方。`TightenOutcome` 里
只有 `tightenedCount`，没有 `remaining` 或 `truncated` 标记。

后果：独占成果数超过 5000 的来源被撤权后，第 5001 条起仍为 `PUBLIC`，
而水位已经推进、事件已经发出，调用方从响应上完全看不出还有没处理完的部分。

### 2.3 恢复来源不还原可见性，也不重新判定

`enabled=true` 只改配置位。被上一节收紧的成果不会恢复；即使要恢复，也不应该「全部公开」——
其中可能有因其它原因（治理未通过、人工限制、另一来源许可失效）而受限的对象。

### 2.4 「还有其他来源」的判据不检查该来源是否仍然有效

`findExclusivelyFromSource` 的 `NOT EXISTS` 子查询只判断「是否存在另一个
`core_achievement_source` 行」，不判断那个来源当前是否仍具备展示许可。
一份已撤销许可的第二来源，足以让一条成果被判定为「非独占」而逃过收紧。

### 2.5 新来源先禁用后启用的路径

`registerSource` 允许 `enabled=false` 登记、随后 `setEnabled(true)` 启用，
启用时不重新检查许可确认状态（`licenseReviewed` 只在登记时检查）。
这条路径是否绕过「首次启用必须确认许可」的约束，需要一并评审。

### 2.6 实测复核（2026-10-17，§2.1／§2.2／§2.4 已复现）

探针：`services/core-service/src/test/java/com/cognitanexus/core/it/SourcePauseConflictProbe.java`，
运行方式 `bash ops/verify/source-pause-conflict.sh`，库为 55432 实例上的 `core_it`。
它**不进默认构建**，因为它断言的是「当前实现做了什么」，而 SRS 要求相反——把它接进门禁，
绿灯会被读成「系统符合需求」。

三条真实输出（原样）：

```
[PROBE 2.1] 暂停 src-a 后：a1(仅 src-a) 可见性=RESTRICTED，b1(有 src-b) 可见性=PUBLIC，收紧条数=1
[PROBE 2.2] 5001 条来源撤权：响应 tightenedCount=5000，仍为 PUBLIC 的条数=1
[PROBE 2.4] src-y 与 src-x 均已停用后：c1 可见性=PUBLIC，来源关联条数=2
```

读法：

- **§2.1**：一次以「上游维护窗口，暂停采集」为理由的调用，把仅依赖该来源的公开成果改成了
  `RESTRICTED`。这与 `AC-FR01-S01-02`（来源暂时停用，历史成果仍可检索）和 `BR-606`
  直接相反。同时有第二个来源的成果不受影响——这一条与「只有完全依赖该来源才收紧」的
  设计一致，说明问题不在收紧范围，而在**暂停这个动作本身就不该收紧**。
- **§2.2**：5001 条独占公开成果、以「许可到期，撤销展示许可」为理由撤权，响应
  `tightenedCount=5000`，第 5001 条仍为 `PUBLIC`。`TightenOutcome` 只有 4 个字段
  （`sourceCode`、`enabled`、`tightenedCount`、`requiredPublicRevision`），没有
  `remaining` 或 `truncated`，调用方从响应上无法知道还有没处理完的部分。
- **§2.4**：先停用 `src-y`（此时 `c1` 还有 `src-x`，保持公开，正确），再停用 `src-x`。
  两个来源都已停用后 `c1` 仍为 `PUBLIC`，而它的来源关联仍是 2 条。`NOT EXISTS` 子查询
  只判断「存在另一条 `core_achievement_source` 行」，不判断那个来源是否仍具备展示许可，
  于是一条已无任何有效依据的成果留在了公开状态。

探针绿的语义是「冲突仍在」。将来实现按本 ADR 拆开后，这三条断言会失败，那时应当改写成
SRS 口径（暂停后仍为 `PUBLIC`、撤权后 0 条残留、第二来源无效时不构成依据），而不是删掉探针。

> **2026-10-18 已按上面这句话执行**：方案 A 落地后，旧的 `SourcePauseConflictProbe` 与
> `ops/verify/source-pause-conflict.sh` 已删除，替换为按 SRS 口径断言的
> `SourceDisplayLicenseProbe` + `ops/verify/source-display-license.sh`（5 项，见 §8.3）。
> 保留这段历史是因为它记录了一个容易被忽略的点：**探针断言的是「当前实现做了什么」，
> 不是「需求要求什么」；实现变更时探针必须跟着改写，否则它会变成一份自我确认的假证据。**

## 3. 候选方案

以下两个方向需要团队选一个，不自定规则。

### 方案 A（推荐）：把两种意图拆成两个操作

- 来源状态改为三值或两个独立标志：`collectionPaused`（暂停采集）与
  `displayLicense`（`GRANTED` / `REVOKED`）。保持向后兼容的做法是保留 `enabled`
  作为采集开关，新增 `display_license_status`。
- 「暂停采集」只影响任务调度，不触碰成果可见性。
- 「撤销展示许可」只影响公开资格，不停止采集（还可以继续为已授权范围更新元数据）。
- 恢复许可时**逐条重新计算**：是否仍有至少一个有效许可的来源、治理状态是否仍允许公开，
  两者都满足才回到 `PUBLIC`。

### 方案 B：保留单开关，但把语义写进接口

`setEnabled` 增加必填的 `intent` 参数（`PAUSE_COLLECTION` / `REVOKE_DISPLAY_LICENSE`），
在服务层分派到不同行为。改动小，但一个布尔仍然承载两种含义，调用方仍需理解区别，
长期看是把问题挪到参数里。

## 4. 大规模撤权怎么处理（无论选哪个方案都要做）

不做「删掉 LIMIT 放进一个大事务」，也不做「先删 LIMIT 再慢慢补」。

- 撤权先进入**可查询的作业**：`source_display_revocation` 记录来源、发起人、依据、
  目标条数、已处理条数、状态、失败原因。
- 公开资格层先可靠阻断：在作业创建的同事务里先把该来源标记为「许可已撤销」，
  公开读路径按该标记拒绝依赖它的成果——阻断是即时的，不需要等逐条更新完成。
- 逐批收紧（每批固定条数，独立事务），批次之间可中断、可重试、可续跑；批内失败只回滚该批。
- 作业完成后核对：仍处于 `PUBLIC` 且仅依赖该来源的成果数必须为 0，作为作业的完成判据。
- 与现有公开水位屏障配合：每一批收紧后推进水位，避免屏障追平后余下成果仍可公开。

### 8.1 落地的四处改动

| 改动 | 位置 | 作用 |
| --- | --- | --- |
| 展示许可独立成列 | 迁移 `V11__source_display_license.sql`：`raw_source_config.display_license_status`（`GRANTED`/`REVOKED`）、`display_license_changed_at`、`display_license_note` | `enabled` 退回纯采集开关；撤权必须留时间点（库级 CHECK 强制），否则事后无法回答「这条成果是撤权之前还是之后下线的」 |

对外端点（`AdminCatalogController`）：

- `PUT /admin/core/sources/{id}/display-license`：撤权或恢复；
- `GET /admin/core/sources/{id}/display-license/revocations`：作业历史；
- `POST /admin/core/sources/{id}/display-license/revocations/{jobId}/resume`：续跑；
- `PUT /admin/core/sources/{id}/enabled`：**行为已变**，只切采集开关，响应里 `displayLicenseTouched=false`、`tightenedVisibilities=0`，并在报文备注里指向 `display-license` 端点。保留旧端点是为了不让既有调用方升级后直接 404，方法已标记 `@Deprecated`。

### 8.2 §2 五条风险的现状

| 原风险 | 现在的行为 |
| --- | --- |
| §2.1 停采集 = 下线历史 | 已消除。`setCollectionPaused` 只改开关、不碰 `visibility`、不推进公开水位（这里没有任何公开数据变化，推水位只会让 query 无谓返回一次 503） |
| §2.2 5001 条只收紧前 5000 条 | 已消除。撤权受理即阻断（许可置 REVOKED 后公开读立刻不含这些成果），逐批收紧每批独立事务、可中断可续跑，完成判据是**残留核对为 0**，不是 `tightened_count == target_count` |
| §2.3 恢复不还原可见性 | 已消除，且按「只放开有归因的对象」实现。无归因的目标数为 0 时作业不会假装恢复成功（见 §8.3 A5） |
| §2.4 判据不检查来源是否仍有效 | 已消除。判据从「存在另一个来源行」改成「存在另一个 GRANTED 来源」；写成「无来源行 OR 存在 GRANTED」而不是「不存在 REVOKED」，否则「A 有效、B 已撤权」的成果会被连坐 |
| §2.5 禁用登记 → 直接启用 | **未消除**，见 §8.4 第 1 条 |

### 8.3 实测（探针 5 项，真实库）

命令：`bash ops/verify/source-display-license.sh`（库为 55432 实例上的 `core_it`，与共享开发库隔离）。
探针类 `services/core-service/src/test/java/com/cognitanexus/core/it/SourceDisplayLicenseProbe.java`
**不进默认构建**：它需要真实数据库与逐条构造的前置状态，进默认构建会让 `mvn verify` 依赖外部实例。
断言从 surefire XML 读，不从控制台截取（控制台是 GBK，中文断行会把断言输出切碎）。

| 编号 | 断言 |
| --- | --- |
| A1 | 暂停采集后成果可见性不变、公开导出仍含这些成果 |
| A2 | 许可置 REVOKED 后，公开导出**立即**不含依赖它的成果（此时 `visibility` 还没被逐批改成 RESTRICTED） |
| A3 | 5001 条仅依赖该来源的公开成果撤权：`target_count=5001`、`tightened_count=5001`、残留=0、作业 `SUCCEEDED` |
| A4 | 已暂停采集的来源仍算有效依据；撤权之后才不算 |
| A5 | 恢复只放开有归因的对象；无归因时目标数为 0，成果保持 RESTRICTED |

输出见下一节（原样粘贴，未删改）。

```
== 运行展示许可探针（连接 55432/core_it）
Tests run: 5, Failures: 0, Errors: 0, Skipped: 0, Time elapsed: 52.77 s -- in com.cognitanexus.core.it.SourceDisplayLicenseProbe
Tests run: 5, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
== 探针输出（取自 surefire XML，避免控制台编码干扰）
[PROBE A1] 暂停 src-a 后：a1=PUBLIC，b1=PUBLIC，导出含两者=true，许可=GRANTED
[PROBE A3] 5001 条撤权：目标=5001 处理=5001 残留=0 完成=true 作业=SUCCEEDED
[PROBE A5] 恢复许可：首次恢复后 d1=PUBLIC（首次断言）；制造无归因受限后再次恢复，目标条数=0，d1=RESTRICTED
[PROBE A4] 暂停 src-y 后撤 src-x：c1=PUBLIC（第一步断言）；再撤 src-y 后：c1=RESTRICTED
[PROBE A2] 许可撤销但未收紧：i1 visibility=PUBLIC，是否在导出中=false
```

怎么读这段输出（**注意 A2 的形状**）：A2 里 `visibility` 仍是 `PUBLIC` 而导出已经不含，
正是「阻断来自许可、不来自逐批收紧」的证据。如果哪天 A2 变成「导出仍含」，说明有人把公开条件
改回了只看 `visibility`，那是一次撤权被拖延到逐批跑完才生效。

### 8.4 仍未解决（不得写成已完成）

1. **§2.5 的路径仍然敞开。** 来源可以「登记为停用 + 许可未审核」，之后调 `setCollectionPaused(false)`
   直接开始采集。原因不在 core：许可审核状态 `license_review_state` 在采集侧
   （`ing_source_run_config`），核心服务看不到它，要堵这条需要 core 调采集侧或把审核状态提到核心库，
   两者都属跨服务契约变更，需单独评审。**现在的行为是：能绕过，且没有任何提示。**
2. **恢复许可的耗时未实测。** 恢复同样分批，但只在探针里跑过小样本；百万级恢复的时长、失败面与
   `RUNNING_RESTORE` 中断后的续跑未测。
3. **撤权不影响已导出但未刷新的一方。** query 侧依赖公开水位与投影重建；若某个下游拿着撤权前的
   快照，本 ADR 的阻断只覆盖本平台自身的读路径。
4. §6 的五条待决策项中，第 2 条（有效许可是否要字段级白名单参与）仍未决。当前判据只看来源级许可。
5. 撤权**不通知**成果的门户管理者（§6 第 5 条），通道仍未建。
