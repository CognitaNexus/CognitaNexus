# ADR-003：站内通知最小闭环

- 状态：**Accepted（2026-10-18，产品负责人授权直接实施；实现记录见 §8）**
- 日期：2026-10-18
- 触发来源：产品评审发现「平台没有任何推送通道」；ADR-001 §8.4 第 2 条（撤权不通知门户管理者，
  无通道）；AC-IMPL-FR05-02 只承诺「申请人可查询决定」（查询 ≠ 送达）
- 影响面：`core-service` 新增 `notification` 模块；`portal`、`governance`、`catalog` 五处业务事件
  接入；前端新增通知中心

## 1. 问题

平台到目前为止的交互模型是「拉」：认领被批准或驳回，申请人不登录查询就不知道；治理员把两条
成果合并，参与学者 portal 的管理者（如果有）不知道自己的档案少了一条；来源撤权导致公开成果
下线，门户管理者看到的是「成果凭空消失」。

这不是锦上添花的问题。平台的治理模型依赖「贡献者愿意来维护自己的数据」——认领、确认、纠错
全部由人驱动。当事人对发生在自己档案上的决定没有感知，就会得出「平台改了我的数据但没人告诉我」
的结论，这正是审计要防的信任损伤。ADR-001 §8.4 第 2 条把「撤权无通知通道」登记为缺陷而不是
延期项，也是这个理由。

## 2. 决策

在 `core-service` 内实现**站内信（inbox）最小闭环**：

1. **表 `core_notification`**，一行一条通知，接收者是账号（`account_id`），只追加 + 标记已读，
   不支持编辑与删除。
2. **系统单向写入**。只有业务事件在自身事务内写通知；用户之间不能互发。这条同时决定了没有
   灌水面：通知的量被业务动作的量天然限制。
3. **同库同事务直接 INSERT**，不经 outbox。理由：outbox 承载的是**跨服务**投影事件，消费者是
   query-service；通知的消费者是账号本人，读的就是 core 自己。让通知走 outbox 只会产生一份
   没有第二读者的副本，还要为它设计投递语义。业务事务回滚时通知一起消失——「合并被回滚却留下
   『你有一条成果被合并』」才是错的。
4. **接口三个**：列表（含未读过滤）、未读数、按 id 批量标记已读。标记已读带 `account_id`
   条件——只能操作自己的通知，横向越权返回 0 行而不是报错（探测别人的通知 id 不应能区分
   「存在但不是你的」与「不存在」）。
5. **不自动清理**。一期通知量与账号量都小；保留策略（如 180 天归档）留待真实规模出现后再定，
   过早定数字没有依据。

## 3. 第一棒接入的五个事件

| 事件 | 写入点 | 接收者 | 通知内容要点 |
| --- | --- | --- | --- |
| 认领裁决 | `PortalService.decideClaim` | 申请人 | 四种结果各自措辞；`NEED_MORE_EVIDENCE` 要告诉申请人「补什么入口在哪」 |
| 门户变更裁决 | `PortalService.decideChange` | 提交者 | 通过 / 驳回与理由 |
| 成果合并 | `GovernanceService.mergeAchievements` | 被合并成果的参与学者中**有活跃认领授权**的账号（按账号去重） | 哪条成果被并入哪条、理由、台账可查 |
| 关系争议裁决 | `ContributionRelationService.resolveByAdmin` | 相关学者（被处置关系的两侧）的活跃认领账号 | 处置结果与理由 |
| 来源撤权完成 | `SourceAdminService` 作业达成 `SUCCEEDED` 时 | 受影响成果的参与学者中活跃认领账号（去重） | 来源名、影响条数、哪些成果因此不再公开 |

合并与撤权的接收者要「按账号去重」：一个账号可能管理多个学者档案、一次合并可能涉及其中两个，
去重后才是一条通知而不是两条内容相同的轰炸。

## 4. 方案比较

- **邮件**：需要 SMTP 基础设施与送达审计，本地课程环境不具备；且邮箱属于个人信息，采集面
  （BR-IMP-11 数据最小化）会扩大。留作后续可选通道，接口上 `kind` 字段已为多通道预留语义。
- **WebSocket / SSE 实时推送**：一期轮询（登录会话期间每 30 秒拉未读数）已满足感知需求；
  实时性不是本问题的核心，「有通道」才是。
- **复用审计表当通知**：审计的读者是审核者与事后复核，不是当事人；两者保留期限、可见性、
  措辞要求都不同，混表会让两边都做不好。

## 5. 风险与边界

1. 站内通知**不承担法律意义上的送达**，界面上只说「站内通知」，不宣称「已告知」。
2. 事务内发通知增大事务体积——单次合并的通知数以「去重后的认领账号数」为上界，实际是个位数
   量级；撤权是作业完成后统一发，不在批次事务里。
3. 通知措辞不得包含他人的证明材料、申请陈述原文等受保护内容，只写结论与去向。

## 6. 验收判据

- 五个事件各自触发后，接收者登录能在通知中心看到对应记录（接口级断言，不依赖界面）；
- 未读数与列表过滤一致；标记已读后未读数减少；
- 跨账号标记已读返回 0 行影响，未读数不变；
- 通知内容不含受保护材料字段；
- 单元测试钉住：合并回滚（抛业务异常）时通知不落库。

## 7. 迁移与结构

迁移 `V12__notifications.sql`；模块 `core/notification`（api / application / domain /
infrastructure 四层，与既有模块一致）。

## 8. 实现记录（2026-10-18）

- 迁移 `V12__notifications.sql` 已应用（flyway_schema_history version=12 success=t）。
- 单元测试 `NotificationServiceTest` 8 项全过；受构造器变更影响的三个既有测试类
  （`ContributionRelationServiceTest` 16、`PortalEvidenceAccessTest` 8、`GovernanceServiceTest`）全绿。
- 接口自检 `tests/api/smoke-notifications.py` 26 项全过，覆盖：未登录拒绝、补证要求通知、
  批准通知、横向越权标记返回 0 行、合并通知按账号去重（真跑一次合并）、nsf 来源撤权
  （真实收紧 55 条）与恢复（回填 55 条）两类通知送达。
- 实现过程中被单测抓到一处真实缺陷并当场修复：服务层最初把去重责任完全交给
  `ScholarClaimantResolver` 实现，自身不兜底；改为服务层用 `LinkedHashSet` 再去重一次。
- 与设计的一处偏差：撤权/恢复通知不在批次事务里逐批发，而是在作业达成终态的同一个事务里
  一次性发送（`drain` 的最终 `setStatus` 事务）；受影响学者集合在恢复方向于批次执行**前**取样
  （恢复会清掉 `display_restriction_source_id`，事后查不到）。
- 语义澄清（验证过程中确认）：来源无独占公开成果时撤权 `targetCount=0`，**没有人收到通知**
  是正确行为——通知跟随真实影响，不发给「碰巧认领了相关学者」的人。
