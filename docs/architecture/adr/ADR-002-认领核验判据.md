# ADR-002：认领核验判据必须先定规则再编码

- 状态：**Proposed（候选规则表，未经团队签认，未实现）**
- 日期：2026-10-17
- 触发来源：老师指导 WB-04；SRS §「系统应接收经评审允许的必要认领证据，支持多证据人工核验；
  不承诺学校邮箱验证或 ORCID 自动认证」；`AC-IMPL-FR05-01/02/03`；BR-IMP-05
- 影响面：`core-service` 的 `portal`（认领）与 `identity`（门户授权）；若采纳，可能涉及证据字段与
  审核说明的结构化，属构件设计阶段，本文件不含 DDL

> 本文件是**候选规则表**，不是已生效的判据，也不是需求结论。表里每一行都写成「建议方向」，
> 需要团队确认后才能进入实现。现行代码没有这些判据——这一点在 §2 逐条给出。
> 不得因为本文件存在就把任何一行当成已实现，也不得用「老师提过」替代签认。

## 1. 问题

认领（claim）的实质是「这个账号是否应当获得某个学者门户的管理权」。它决定的是写入权限，
不是展示偏好，所以「凭什么相信申请人」必须有一个可复核的判据，而不是审核人临场决定。

现状能执行人工审批，但**不能证明「哪些证据足够」**：一份申请只要说明非空就可以进入待审队列，
审核者批准时系统不看任何证据。这带来两个具体后果：

1. 同一个审核者在不同时间可能对同类申请作出不同结论，且事后无从解释差异；
2. 无法回答「这条授权是凭什么批的」——审计里只有一句自由文本理由。

## 2. 现状（代码可见）

| 环节 | 位置 | 实际做的事 | 缺的东西 |
| --- | --- | --- | --- |
| 提交 | `PortalService.submitClaim` | 校验认领说明非空、学者存在且未合并、幂等键、同一账号同一学者不重复开单 | 不检查证据种类，也不要求必须附材料 |
| 追加材料 | `PortalService.attachEvidence` → `EvidenceStorage` | 文件落受控卷、校验类型、登记哈希与大小；原文不入审计 | 材料与「证明什么」没有关联：一份单位主页截图和一份伪造的公函在库里长得一样 |
| 补证 | `PortalService.resubmit` | 只有 `NEED_MORE_EVIDENCE` 状态可重提，回到待审 | 补了什么、补得够不够，没有结构化记录 |
| 裁决 | `PortalService.decideClaim` | 四种动作 `APPROVE`／`REJECT`／`NEED_MORE_EVIDENCE`／`DISPUTE`，理由必填 | 批准时不读证据；四类动作与证据的对应关系未定义 |
| 互斥 | `PortalService.approve` + `uk_iam_portal_authority_active` | 已有生效授权时不转移，落 `DISPUTED`；并发由部分唯一索引裁决 | 这一层已经可靠（T10–T12 有真实数据库验证），不是本 ADR 要解决的问题 |

所以本 ADR 只讨论一件事：**批准之前，什么算证据够**。互斥、并发、审计留痕已经在上一批做完了。

## 3. 需求原文与边界

- 「系统应接收经评审允许的**必要**认领证据，支持**多证据人工核验**；**不承诺学校邮箱验证或
  ORCID 自动认证**。」——这句同时定了下限和上限：必须有证据、必须人工核验、不得宣称做了外部认证。
- 「不展示他人申请材料」——材料只对申请人本人与有权处理的审核人可见。
- 认领只授予**门户管理权**，不把该人全部同名成果自动改为本人确认（同名不合并是既有红线）。

结论：**任何形式的自动授权都超出当前 SRS**。指导文档里的「低负担核验路径」也只能是
「人工核验的辅助」，不能变成「验证通过即自动授予」。

## 4. 候选规则表（待签认）

六种情形，每一行给三样东西：建议方向、必须先解决的问题、现行实现能不能表达。第三列是判断
「能不能先做界面与流程、把自动化留到以后」的依据。

| # | 情形 | 建议方向 | 必须先解决的问题 | 现行实现能否表达 |
| --- | --- | --- | --- | --- |
| C1 | 只提供姓名、主页链接或公开 ORCID 字符串 | 不据此授权；缺证明则 `NEED_MORE_EVIDENCE` 或人工核验 | 「公开资料证明不了控制权」这一条要写进审核指引，否则仍会被当成证据 | 能（只是审核人不用它），但系统无法阻止把这类材料当唯一依据批准 |
| C2 | 申请人能证明控制某个作者邮箱，且该邮箱出现在允许使用的来源记录里 | 可评审为低负担核验路径（仍需人工确认） | 一次性挑战的有效期与防重放；来源邮箱是否获准处理；姓名／机构冲突怎么办 | 不能。没有邮箱验证能力，也没有「来源记录里的邮箱」这一字段 |
| C3 | 申请人通过 ORCID 授权登录，确认所控制 ID 与档案 ID 一致 | 可评审为强证据之一 | OAuth 回调校验、ID 绑定、撤销与冲突；**不得**把「输入 ORCID」当授权登录 | 不能。现在只能存一个 ORCID 字符串，无法区分「填写」与「验证过」 |
| C4 | 无邮箱／ORCID，但有其他可核实证明（单位公函、人事页面、导师确认等） | 人工路径 | 明确允许的材料清单、核对对象、真实性局限、补充理由与申诉方式 | 部分。能存文件，但存不了「这是什么、核对谁、结论是否可核」 |
| C5 | 门户已有生效管理人 | 争议处理，保留原授权 | 已有能力（`APPROVE` → `DISPUTED`，不转移） | 能，且已由 T10–T12 验证 |
| C6 | 材料不足、矛盾、无法判断 | 补充／驳回／争议，给可操作理由 | 不给空泛的「审核不通过」；不默认放行 | 能落状态，但理由仍是自由文本，无法统计「因为缺什么被驳回」 |

**C5 是唯一可以直接照现状用的行**。其余五行都需要规则确认；C2／C3 还需要外部能力，
而 SRS 已明确不承诺。

## 5. 需要团队签认的六件事

1. **证据种类**：哪些材料算「必要证据」，各自证明什么（控制权／任职关系／成果归属）。
2. **核对对象**：审核人去哪里核对——来源记录里的作者信息、单位公开页面、还是申请人自述。
3. **通过／补充／驳回的边界**：什么情况必须补充而不是直接驳回；什么情况必须争议。
4. **外部验证不可用时怎么降级**：邮箱挑战发不出去、ORCID 不可达时，是否退回纯人工，
   以及要不要在界面上明确告知「本次未做外部验证」。
5. **审核说明**：是否要求按结构填（缺什么、核对了什么、结论依据），还是继续自由文本。
6. **材料访问与保存期限**：谁能看、看多久、删除后审计里留什么（现在只留哈希与大小）。

## 6. 最小落地（不需要外部能力、不引入自动授权）

先说明一件已经做了的事，避免重复劳动：**审核界面已经显示了材料份数与受保护下载链接**。
`AdminPortalController` 的待审查询会用 `claimView(claim, evidences)` 带上材料元信息
（只给 `contentType`、`sizeBytes`、`contentHash` 与受保护下载路径，不给 `fileRef` 或磁盘路径），
`ReviewView` 渲染成「材料 N 份」，没有材料时提示「仅凭说明不足以核验身份时，请选择需补证，
并在审核意见里写明需要哪一类材料」。所以这一步不需要再做。

剩下可以立刻做的：

1. **把「有没有材料」升级成「材料证明了什么」**：现在的界面只回答「几份」，不回答「哪一份在证明
   控制权、哪一份在证明任职关系」。这一步需要在材料上挂一个种类，涉及字段，按规范走构件设计评审。
2. **把审核说明结构化**：`decideClaim` 的 `reason` 之外增加「核对对象」与「缺失项」两个可选字段，
   仍不阻断流程，先积累一批真实理由，用它反推规则。同样涉及字段，需评审。
3. **明确标注未做外部验证**：任何涉及邮箱／ORCID 的表述都要写成「申请人填写」，不得写成「已验证」。
   已核对：`PortalView` 里没有「已验证」字样（`grep -n "已验证" frontend/src/views/PortalView.vue`
   无输出），所以这一条当前不构成缺陷；但将来加邮箱／ORCID 入口时必须守住它。**这一条现在就能做，
   不涉及 DDL。**
4. **C2／C3 不进实现**，直到有人决定引入外部验证并承担其运维与合规成本。测试替身可以用，
   但必须明示是替身，不得写成「已完成 ORCID 认证」。

第 3 步不涉及 DDL，属于可以独立评审的小改动；第 1、2 步涉及字段，按规范要走构件设计评审。
换句话说：**在不签认判据、不改表的前提下，已经没有多少「安全的空转空间」了**——再往下走
就必须先有人决定 C1–C6 的边界。

## 7. 本文件不做的事

- 不修改任何代码、配置或数据库状态。
- 不引入 OAuth、邮件服务或任何外部身份认证。
- 不改变 `ClaimRequest` 的状态集合与互斥规则（那部分已由 T10–T12 验证）。
- 不把本文件的任何一行写成「已生效判据」；在签认之前，审核仍是人工判断，
  而「人工判断没有记录依据」这件事本身就是当前要解决的问题。
