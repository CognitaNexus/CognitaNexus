## 2. A 阶段：认领互斥（T10／T11／T12）

### 2.1 为什么这一项必须进真实数据库

认领互斥的结论全部落在「同一门户到底有几条 `ACTIVE` 授权」「两笔并发插入谁被拦下、事务回滚到哪里」「被拦下的那笔会不会把已批准申请改判成争议」上。这三条由部分唯一索引 `uk_iam_portal_authority_active`（`ON iam_portal_authority (scholar_id) WHERE status = 'ACTIVE'`）与行锁的交互决定，Mock 仓储只能复述实现里的 `if`。

新增 `services/core-service/src/test/java/com/cognitanexus/core/it/ClaimConcurrencyIT.java`，5 个用例：

| 用例 | 断言的东西 |
| --- | --- |
| `competingClaimsLeaveExactlyOneActiveAuthority` | 两账号各自申请、两审核者并发批准：全库只剩 1 条 `ACTIVE`，败者申请落 `DISPUTED`，授权不转移，学者状态 `CLAIMED` |
| `sameClaimApprovedTwiceDoesNotDowngrade` | 同一份申请被两人同时批准：只 1 条授权，申请仍是 `APPROVED`，不出现「已批准又被改判争议」 |
| `secondActiveAuthorityBlockedUntilFirstCommits` | 受控双事务：先插入未提交时，第二笔在索引上阻塞，先到者提交后返回 0 行影响而非抛异常 |
| `partialUniqueIndexIsWhatEnforcesUniqueness` | 反证：事务内删掉索引后同一语句直接 `ON CONFLICT` 定位失败（42P10），回滚后索引仍在 |
| `revokedAuthorityDoesNotBlockRegrant` | 撤销后允许重新授予（部分索引只约束 `ACTIVE`），且撤销是留痕不是删行 |

**重叠是受控制造的**：`@BeforeEach` 在 `iam_portal_authority` 上装一个只做 `pg_sleep(0.4)` 的触发器，让两笔插入几乎同时抵达索引，从而稳定走到「两边都通过了前置查询、由唯一索引裁决」这条路径。触发器只加延迟，不改约束、不改数据、不参与断言。没有它时两笔事务经常自然串行，测试看似通过却只验证了 `if` 分支。

### 2.2 先红：并发竞争不留痕

首轮执行前先加了一条断言：不管走哪条竞争路径，`aud_audit_event` 里必须有一条可分辨的 `CLAIM_COMPETITION_DETECTED`（`after_value->>'detection'` ∈ {`PRE_CHECK`, `UNIQUE_INDEX`}）。

失败原文（`failsafe-reports`）：

```
ClaimConcurrencyIT.competingClaimsLeaveExactlyOneActiveAuthority:195
竞争认领必须在审计里留一条可分辨的痕迹，实际为 []
```

原因：`PortalService.approve` 的「前置查询发现已有授权」分支写了审计，而「插入被唯一索引拦下」的分支只做了状态迁移。结果是并发场景下只剩「申请变成 DISPUTED」这一个结果——事后无法区分「当时确有并发」与「有人手工改判」，也无法解释为什么没有第二条授权。

### 2.3 修复与复跑

`PortalService.approve` 的两条竞争路径各自补上审计，并用 `detection` 字段区分抑制发生在哪一步；索引路径额外记下 `constraint=uk_iam_portal_authority_active`。修复后：

```
Tests run: 5, Failures: 0, Errors: 0, Skipped: 0  — in ClaimConcurrencyIT
```

同时用「删索引 → 42P10」反证了唯一性确实由索引保证，不是应用代码里的判断。

### 2.4 未覆盖

- 未验证「审核者审核自己提交的申请」这类身份冲突（当前实现没有这条规则，属规则待定）。
- 未做 3 个以上审核者对同一批申请的竞争（本批只做 2 个）。
- 未测授权撤销与并发批准的交叉（撤销时另一笔正在批准）。

## 3. B 阶段：100 万可检索去重成果

### 3.1 造数方式与它不能代表什么

`tests/perf/seed-core.sql` / `seed-query.sql`（固定种子 `0.42`，可重跑得到同一批数据）：

- 标题由 400 个词根按 `power(x,2)` 偏斜拼成（低编号词更常出现），6 个词位按「行号+词位」哈希派生；
- 类型比例：论文 55% / 专利 15% / 项目 20% / 获奖 10%；`PUBLIC` 92%；`EFFECTIVE` 90%；年份 1990–2026 且 5% 未知（留 `NULL`，不补 1 月 1 日）；

- 合作边只由论文且关系合格的作者对生成，两端按字典序。

**第一次造数造错了，值得记下来**：标题最初写成不带外层引用的标量子查询，PostgreSQL 只求值一次，10 万行得到**同一条标题**。当时的表征是「关键词检索要么全命中要么零命中」，`EXPLAIN` 里全是 `Parallel Seq Scan` 且 `rows=0`——看起来像索引问题，其实是数据退化。修正为按行号派生的相关子查询（`LATERAL`）后，热门词命中率 26.9%。

### 4.2 根因链（按证据顺序）

1. **统计概览单请求就要 34–64 秒**。绕过负载生成器直接 `curl`：`analytics/overview` 两次分别 64.5 s、34.2 s；`AnalyticsService.overview` 在一次请求里串了十余个全量聚合（5 个 count、byType、byYear、byNature、topOrganizations、topTopics、topVenues、citationsBySource），与 §3.3 中单项 4.8–5.9 秒的测量一致。
2. **慢请求把连接池占满**。压测期间每 20 秒采样一次 `pg_stat_activity`：`active=16 / idle=6` 稳定不动——16 正是 query 服务 `maximum-pool-size`。
3. **其余请求在 5 秒内拿不到连接，直接 500**。日志里 3,848 条 `CannotGetJdbcConnectionException: Failed to obtain JDBC Connection`，76 条 `canceling statement due to user request`（客户端 20 秒超时后断开）。
4. **因此 100 VU 的 P95 反而低于 50 VU**（11.1 s vs 18.5 s）：负载越高，越多请求在 5 秒的**连接获取超时**上快速失败，而不是等慢查询跑完。这是 fail-fast 的表征，不是性能改善。这一条必须写明，否则会被读成「加负载反而更快」。

### 4.3 结论

在「100 万合成成果 + 默认数据库参数 + 三个进程同机」的条件下，**工程的 NF02 目标（100 活跃用户、P95≤2s）未达到**，且失败形态是级联的：一个慢接口拖垮整条公开读路径，而不是只有它自己慢。

不把「提高连接池」「加超时」当作解决方案：那只会把 500 变成更长的排队，P95 仍然是几十秒。要动的是统计概览的口径与实现（预计算／缓存／拆接口），以及连接耗尽时的错误语义（当前是 500，按语义应是 503 + 重试提示）。这两项都属设计变更，需评审后单独做。

### 4.4 500 万（C 阶段目标量）未执行

原因不是时间不够，而是**先证伪再扩容**：100 万时统计概览已 30 秒以上、连接池已耗尽，扩到 500 万只会把同一个结论放大 5 倍，得不到新的信息。按 §7.1「先证明正确再扩大规模」，500 万应在上面的统计口径问题修掉之后再执行。这是本批明确未达的一项，不计入通过。

## 5. 恢复

### 5.1 T32：投影链路的重复／乱序／毒事件（`ProjectionRecoveryIT`）

新增 `services/query-service/src/test/java/com/cognitanexus/query/it/ProjectionRecoveryIT.java`，4 个用例，全部在真实数据库上跑：

| 用例 | 断言 |
| --- | --- |
| 重复投递 | 同批出现两次折叠为 1 条；跨批重投 `received=0`、`duplicated=1`、`applied=0`；inbox 1 行、投影 1 行、水位只推进一次 |
| 乱序抵达 | 先到 revision=3 时 `receivedRevision` 停在 0、`highestSeenRevision=3`、`receiveLag=3`（`publishLag` 为 0，积压不在发布侧）、`pendingRemaining=true`，发布 `DEFERRED`；缺口可被 `firstReceivedRevisionAfter` 指出为 3；补齐 1、2 后同一批把 3 一起投影，`publishedRevision=3` |
| 毒事件 | `schemaVersion=99` 被隔离，发布水位停在它之前；`oldestIsolatedRevision=2`、`countByState.ISOLATED=1`；其后的修订不被提前投影 |
| 恢复 | `rearmFailed` 只重新入队 `FAILED`，不会把 `ISOLATED` 悄悄改回 `RECEIVED` |

断言直接用**接收回执**（core 侧唯一能看到的东西），因为「received 表示已接收、`publishedRevision` 之前才对外可查」这条语义本身就是要验证的对象。

#### 5.1.1 首轮两条失败：回执把「收到」说成「生效」

首轮 4 个用例中 2 条失败，两次失败都不是测试写错，是实现里的口径错了：

| 失败用例（行） | 真实输出 | 缺陷 |
| --- | --- | --- |
| `duplicateDeliveryHasSingleBusinessEffect`（`second.received()`） | `expected: 0 but was: 1` | 回执的 `received` 取的是「本批折叠后的条数」而不是「实际落库条数」。整批重复时它回 `received=1, duplicated=1`——同一事件既被算作已接收又被算作重复，`received + duplicated` 也不等于请求条数。 |
| `outOfOrderRevisionStallsUntilGapFilled`（`pendingRemaining()`） | `Expecting value to be true but was false` | 积压判据写成 `receivedRevision > publishedRevision`。缺口未补齐时两者都停在 0，于是**在最该报告积压的时刻回执「没有积压」**，而修订 3 正躺在 `qry_inbox_event` 里没被投影。 |

修法（行为改动都在 `InboxReceiver.receive`，另把字段口径写进 `BatchReceipt` 的 javadoc）：

1. `received = inserted`（真正落库条数），`duplicated = records.size() - inserted`，两者相加才是本批折叠后的条数；`BatchReceipt` 的字段口径补进 javadoc，避免下次再被读混。
2. `pendingRemaining = highestSeenRevision > publishedRevision`。改用「见过的最大修订」后，正常积压与缺口停摆两种情形都为 `true`，并且不会出现「全部应用完仍报有积压」的假阳性（追平时三者相等）。

修完 `Tests run: 4, Failures: 0`。这两条正是「必须断言回执而不是断言库」的理由：库里的行数、水位值在首轮全部正确，错的只是**对外说出口的那句话**，而 core 与运维读的正是这句话。

#### 5.1.2 记录自身的更正

本记录首稿把乱序用例的积压写成 `publishLag=3`，实际 `publishLag = received - published = 0`；积压坐在 `receiveLag = highestSeen - received = 3`。这是记录写错，不是代码错，但说明「积压」不加限定就会被读成发布侧。现表已拆成两个字段分别断言。

**未覆盖**：真实跨服务链路（core 的 Outbox 投递器 → query 的 `/internal/v1/inbox`）没有在压测规模下跑；本批只验证了接收端与发布端在同库内对自己状态的处置。故障演练没有做「暂停消费者再恢复」的网络级演练，只做了状态级注入。

### 5.2 T33：备份与恢复演练（`ops/perf/restore-drill.sh`）

在隔离实例上对 100 万数据的两个库各做一次 `pg_dump`（custom 格式）→ 恢复到新库 → 核对：

| 库 | dump 用时 | dump 体积 | restore 用时 | 表数 | 逐表行数 |
| --- | ---: | ---: | ---: | ---: | --- |
| `core_perf` → `core_perf_restore` | 14 s | 38 MB | 56 s | 36 | 一致 |
| `query_perf` → `query_perf_restore` | 23 s | 91 MB | 100 s | 12 | 一致 |

结构与数据之外还核对了三件事：

- **约束还在**：`uk_core_paper_doi_norm`、`uk_iam_portal_authority_active`、`pk_qry_achievement`、`pk_qry_coauthor_edge`、`ix_qry_achievement_title_trgm`、`qry_consumer_state` 的外键都在。
- **规则还在**：在恢复库里提交一条「可发布但缺类型扩展」的 `core_achievement`，延迟触发器拒绝并回滚（残留 0 行）。
- **数据可用**：同一条公开检索在源库与恢复库的命中数均为 828,174；`EXPLAIN ANALYZE` 在恢复库能正常执行（477 ms / 595 ms，后者为冷统计信息）。

**演练本身踩了两个坑，都已修进脚本**：

1. 含中文的 SQL 用 `psql -c` 传——Windows 下 argv 按 ANSI 码页转码，UTF-8 中文被破坏，报 `invalid byte sequence for encoding "UTF8": 0xbb`；
2. 用 `DO $$ ... RAISE ... $$` 去验证延迟触发器——延迟触发器在**提交**时检查，块里的 `RAISE` 会先于提交执行，检查根本没发生。首次演练因此给出「触发器未生效」的假结论；改成一条独立的自动提交 `INSERT` 后，正确得到「提交被拒绝、残留 0 行」。

**未覆盖**：没有测「从备份重建投影」（需要 core 导出口 + 事件回放，属重建链路，本批未动）；没有测恢复到另一台机器的时间线；没有测增量备份与 WAL 归档。

## 7. 需要评审的三个决定（不是本批能自行定的）

1. **统计概览的口径与实现**：现在一次请求串十余个全量聚合。可选方向（预计算表／带失效的缓存／拆成多个接口由前端按需拉取）各有利弊，涉及「统计口径可追溯」与「缓存不得让撤权延迟生效」两条约束，须单独评审。
2. **连接耗尽时的语义**：当前是 5 秒后返回 500。按业务语义应为 503 + `Retry-After`，并让前端可区分「服务繁忙」与「请求有误」。
3. **索引方案**：本批测量显示瓶颈在聚合不在访问路径，因此没有提交迁移。若后续仍要做，需按 §7.4 给出查询收益、写入成本与体积的对比。
