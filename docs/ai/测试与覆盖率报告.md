### 4.1 性能基线：本轮实测两次，各有一条链路超限

`tests/api/smoke-perf.py` 的判据是「单用户串行、当前数据规模下每条链路 P95 不超过 2 秒」这个**工程上限**，
不是验收指标。文件头写明：它测的是 9638 条公开成果、单调用者、无并发排队，**不得据此宣称 P95 ≤ 2 秒达标**。本报告同样不这么写。

本轮连跑两次（间隔约 4 分钟，中间无其它脚本），结果不一致：

| 链路 | 第一次（16:27）P50 / P95 | 第二次（16:31）P50 / P95 |
| --- | --- | --- |
| 关键词检索 | 34.0 / 55.8 ms | 34.7 / 53.6 ms |
| 列表翻页 | 28.5 / 45.5 ms | 25.1 / 39.8 ms |
| 分面筛选 | 27.3 / 40.8 ms | 25.5 / 42.0 ms |
| 统计概览 | 421.4 / 477.4 ms | 420.5 / 455.4 ms |
| 领域洞察 | 541.3 / **2109.7 ms**（FAIL） | 467.7 / 587.8 ms |
| 合作网络 1 跳 | 112.5 / 193.7 ms | 82.8 / 101.9 ms |
| 合作网络 2 跳 | 1255.6 / 1454.5 ms | 1954.8 / **5723.3 ms**（FAIL） |
| 成果详情 | 8.3 / 20.6 ms | 7.8 / 22.1 ms |
| 项目结论 | 通过 15 / 失败 2 | 通过 15 / 失败 2 |

两次都是 17 项里 15 项通过、2 项失败（超限链路 + 「所有链路 P95 不足上限一半」的汇总项）。
**必须如实说明的三点：**

1. 超限的不是同一条链路。第一次是领域洞察（刚跑完全量重建，统计与缓存处于冷态），第二次是合作网络 2 跳（P50 也从 1256ms 涨到 1955ms，整条链路都慢了）。这种「换一条链路超限」的形状说明当前环境存在强抖动，不能挑一次通过的结果作为结论。
2. 结算性结论是：**当前数据规模下，统计概览（P50 约 420ms）与网络 2 跳（P50 1.2–2.0 秒）本身就很重**，离 2 秒上限没有余量。快速点选类链路（检索、翻页、分面、详情）稳定在 20–60ms，与它们不是一个量级。
3. 抖动本身值得排查（重建后的统计信息、连接池预热、后台投影消费都在候选原因里），但本轮没有做归因实验，因此不写「根因是 X」。**状态：未归因。**

### 5.2 门禁是真的在拦（反证）

`bash ops/verify-coverage-gates.sh --skip-build` 做两件事：打印真实覆盖率；把每条门禁阈值临时提到不可能达到的 1.01，要求**必须失败**。

```
OK  services/core-service/jacoco-check-governance 在 1.01 下失败 —— 门禁拦到了实际包
OK  services/core-service/jacoco-check-catalog-domain 在 1.01 下失败 —— 门禁拦到了实际包
OK  services/query-service/jacoco-check-analytics 在 1.01 下失败 —— 门禁拦到了实际包
结果：3 条门禁全部真实生效，且覆盖率均不低于 80%。
```

为什么需要这条反证：JaCoCo 的 `includes` 相对 `element` 匹配，写错就会匹配到空集合，而**空集合一律判为通过**。
本项目踩过两次（`element=BUNDLE` 比 bundle 名；`element=PACKAGE` 时 `包名.*` 只命中子包）。规则与原因写在
`services/core-service/pom.xml` 的注释与 `ops/verify-coverage-gates.sh` 文件头。

### 5.3 单元测试覆盖率的边界

覆盖率只统计 JVM 内单元测试执行过的代码。接口自检（`tests/api/`）打的是运行中的服务，不产生 JaCoCo 数据。
所以「全服务行覆盖率 40.35% / 34.04% / 26.93%」不代表这些服务没被验证过，只代表单元测试没覆盖到的部分
（Controller、Mapper、投影消费、采集执行器）靠接口自检验证。两个数字不能互相替代，也不能只报高的那个。

### 11.2 这两层用例抓到的实现缺陷（已修）

1. **接口回执把「收到」说成「生效」**：`InboxReceiver` 的 `received` 取本批折叠后的条数而不是实际落库条数，整批重复时回 `received=1, duplicated=1`；`pendingRemaining` 用 `received > published` 判断，缺口停摆时两者都为 0，于是回执回答「没有积压」，而事件正躺在库里等一条永远不会到来的前序修订。改为 `received = inserted`、`pendingRemaining = highestSeen > published`，并把字段口径写进 `BatchReceipt` 的 javadoc。**库里的行数与水位在修复前全都是对的**——错的只是对外说出口的那句话，这也是断言回执而非断言库的价值。
2. **认领竞争的并发路径不留审计**：走部分唯一索引拦下这条路径时原来不写任何审计，事后无法区分「当时确有并发」与「有人手工改判」。已补 `CLAIM_COMPETITION_DETECTED`（`detection=UNIQUE_INDEX`，附约束名），先由断言变红再修绿。

## 13 语义冲突探针（ADR-001，不计入上表计数）

`SourcePauseConflictProbe`（`services/core-service/src/test/java/com/cognitanexus/core/it/`，3 项）
是为了给 ADR-001 取证而写的，**不属于验收用例，也不在 514 / 29 里**：

- 类名不以 `Test` / `IT` 结尾，Surefire 与 Failsafe 的默认扫描都不会收集它，`mvn verify` 的计数不变。
- 运行方式：`bash ops/verify/source-pause-conflict.sh`（要求 55432 实例在跑）。
- 它断言的是「当前实现做了什么」，而 SRS 要求相反。**探针全绿表示冲突仍然存在**，不是通过验收。
  这一点在类注释、脚本头注释与 ADR §2.6 三处重复写明，因为一行绿色的测试最容易被后继者误读。

三条实测结论（原样输出见 ADR §2.6）：暂停采集把独占来源的公开成果改成 RESTRICTED；
5001 条撤权只收紧 5000 条且响应无剩余标记；两个来源都停用后成果仍残留公开。

如果将来有人把这类探针接进 CI 门禁，那就等于用「实现现状」冒充验收标准——ADR-001 明确禁止。

**计数时的一个坑**：手动跑过一次探针后，`target/surefire-reports/` 里会留下它的报告文件，而
`mvn verify` 不会清 target。此时按 `<testcase>` 累加会多出 3 项（实测为 308 而不是 305），
看上去像「探针被收集了」。判断办法看报告文件的修改时间：`verify` 没有刷新它，就说明没跑。
统计脚本应排除 `*Probe`。
