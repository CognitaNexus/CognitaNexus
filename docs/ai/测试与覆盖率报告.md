## 1 本轮实际执行的范围

1. 起整栈（`bash ops/local/stack.sh`，后台任务承载），确认七个端口就绪；
2. 全量构建 + 单元测试 + 覆盖率门禁：`./mvnw -B -ntp verify`（**不再跳过 `spotless:check`**，见下）；
3. 集成测试（真实 PostgreSQL）：`./mvnw -B -ntp verify -Dcn.it.skip=false`；
4. 接口自检：core、ingestion、query、contract、redlines、claim-evidence 与本轮新增的 fr-additions；
5. 展示许可探针：`bash ops/verify/source-display-license.sh`（ADR-001 方案 A 的 5 条语义）；
6. 前端类型检查 `vue-tsc --noEmit`；容器编排静态校验 `bash ops/verify/compose-smoke.sh`。

**本轮 `mvn verify` 失败过两次，都是真实缺口，不是环境问题：**

1. **格式门禁**：`spotless:check` 报了格式偏差，全部落在本轮改过的 Java 文件上。上一份报告里
   「存量代码有 26 个文件格式偏差、未获授权批量格式化」这条前提本轮已不成立（本轮实测该模块 0 违规），
   因此**不再用 `-Dspotless.check.skip=true`**，而是对本轮改动的文件执行 `spotless:apply`。
   没有对无关文件做批量格式化。
2. **覆盖率门禁**：`query.analytics.api` 行覆盖 66%（门禁 80%），原因是新增的 `GET /keywords`
   只有服务层测试、控制器没有。补 `PublicAnalyticsControllerTest` 2 项后恢复 100%。

两次失败都不是「重跑就好了」，改动都留在仓库里。

### 4.1 性能基线：本轮实测两次，各有一条链路超限

`tests/api/smoke-perf.py` 的判据是「单用户串行、当前数据规模下每条链路 P95 不超过 2 秒」这个**工程上限**，
不是验收指标。文件头写明：它测的是 9638 条公开成果、单调用者、无并发排队，**不得据此宣称 P95 ≤ 2 秒达标**。本报告同样不这么写。

本轮连跑两次（间隔约 4 分钟，中间无其它脚本），结果不一致：

| 链路 | 第一次（16:27）P50 / P95 | 第二次（16:31）P50 / P95 |
| --- | --- | --- |
| 关键词检索 | 34.0 / 55.8 ms | 34.7 / 53.6 ms |
| 列表翻页 | 28.5 / 45.5 ms | 25.1 / 39.8 ms |
| 分面筛选 | 27.3 / 40.8 ms | 25.5 / 42.0 ms |
| 统计概览 | 421.4 / 477.4 ms | 420.5 / 455.4 ms |
| 领域洞察 | 541.3 / **2109.7 ms**（FAIL） | 467.7 / 587.8 ms |
| 合作网络 1 跳 | 112.5 / 193.7 ms | 82.8 / 101.9 ms |
| 合作网络 2 跳 | 1255.6 / 1454.5 ms | 1954.8 / **5723.3 ms**（FAIL） |
| 成果详情 | 8.3 / 20.6 ms | 7.8 / 22.1 ms |
| 项目结论 | 通过 15 / 失败 2 | 通过 15 / 失败 2 |

两次都是 17 项里 15 项通过、2 项失败（超限链路 + 「所有链路 P95 不足上限一半」的汇总项）。
**必须如实说明的三点：**

1. 超限的不是同一条链路。第一次是领域洞察（刚跑完全量重建，统计与缓存处于冷态），第二次是合作网络 2 跳（P50 也从 1256ms 涨到 1955ms，整条链路都慢了）。这种「换一条链路超限」的形状说明当前环境存在强抖动，不能挑一次通过的结果作为结论。
2. 结算性结论是：**当前数据规模下，统计概览（P50 约 420ms）与网络 2 跳（P50 1.2–2.0 秒）本身就很重**，离 2 秒上限没有余量。快速点选类链路（检索、翻页、分面、详情）稳定在 20–60ms，与它们不是一个量级。
3. 抖动本身值得排查（重建后的统计信息、连接池预热、后台投影消费都在候选原因里），但本轮没有做归因实验，因此不写「根因是 X」。**状态：未归因。**

#### 4.1.1 同日补记：两条超限均已归因并修复，最终 17/17 通过

上表「未归因」的抖动在当天上午复现并恶化（统计概览 P95 一度 8186ms，合作网络 2 跳 4191ms），逐层排查后确认了**两个相互独立的根因**，均已有实测证据与对应修复：

**根因一：Windows 下并行查询的 worker 进程创建开销（影响统计链路）。**
`qry_contribution_org` 增长到 18.9 万行后，规划器开始给统计计数选并行计划；PostgreSQL 在 Windows 上每次执行并行计划都要为 Gather 节点拉起 worker 进程，实测单次 1～2 秒。同一条 NOT EXISTS 计数：并行计划 4.5～8.3 秒，`max_parallel_workers_per_gather=0` 后 **44～84ms**。修复：query 服务连接初始化追加 `SET max_parallel_workers_per_gather = 0`（`application.yml`，注释写明取舍与迁移条件）。统计概览由 4～8 秒回到约 1 秒。

**根因二：OR 形状扩边 SQL 的计划对 ID 集合敏感（影响网络链路）。**
`scores (scholar_a IN (...) OR scholar_b IN (...))` 同一形状的语句，有的 ID 集合走 54ms 双侧位图计划，有的被判成「按主键扫整代再过滤」的 2.2 秒计划——**字面量与绑定参数都会踩中，服务端无法干预**。它还与 PgJDBC 的服务端预处理缓存叠加：CHUNK 提到 1000 后等长块产生相同 SQL 文本，第 6 次执行起切到泛型计划（psql 实测泛型 3890ms vs 自定义 71ms），最短路径 BFS 因此稳定超过 1 秒时间预算（GRAPH_TIMEOUT，smoke-query 4 项失败）。修复分两层：

- `ScopedGraphLoader.CHUNK` 400 → 1000（978 参数单条计划实测 35ms，查询次数减半）；
- 扩边 SQL 拆成 `listEdgesWhereScholarA` / `listEdgesWhereScholarB` 两条单列 IN（计划与索引一一对应，三种执行方式实测 1～19ms），`ScopedGraphLoader` 按对去重合并——两支对同一对返回的强度相同（各自统计该对全部合格论文），合并不重复计数。

**总览另加修订键备忘缓存**：统计概览每次请求跑 12 条聚合 SQL，全量重算 1.2～2.2 秒。聚合是「某个已发布修订下的确定性产物」，现按「代 + 口径 + 已发布修订」缓存最近一次结果；护栏的权威水位**每次照读**（资格线性化不受影响），水位推进键即失效。缓存行为有 2 个单元测试钉住（同修订只算一次且护栏仍每次读；修订推进/口径切换即重算）。

**修复后最终基线（2026-10-18 上午，规模 12249 条，`python tests/api/smoke-perf.py`）**：17 项全部通过，最慢链路领域洞察 P95=497ms，合作网络 2 跳 P95=669ms，统计概览回到秒内。同轮 `smoke-query.sh` 90 项全部通过（含此前因路径超时失败的 4 项）。

- 类名不以 `Test` / `IT` 结尾，Surefire 与 Failsafe 的默认扫描都不会收集它，`mvn verify` 的计数不变。

  这一点在类注释、脚本头注释与 ADR §2.6 三处重复写明，因为一行绿色的测试最容易被后继者误读。

三条实测结论（原样输出见 ADR §2.6）：暂停采集把独占来源的公开成果改成 RESTRICTED；

如果将来有人把这类探针接进 CI 门禁，那就等于用「实现现状」冒充验收标准——ADR-001 明确禁止。

**计数时的一个坑**：手动跑过一次探针后，`target/surefire-reports/` 里会留下它的报告文件，而
`mvn verify` 不会清 target。此时按 `<testcase>` 累加会多出 3 项（实测为 308 而不是 305），
看上去像「探针被收集了」。判断办法看报告文件的修改时间：`verify` 没有刷新它，就说明没跑。

### 14.4 本轮测试抓到的三个真实缺陷（全部已修，均不是「测试写错」）

1. **单成果配额形同虚设**：`PublicCorrectionService` 把来源地址拼进了「单成果 24 小时配额」的计数键，

   并在类注释里写明它封的是「慢速滴灌」以及「配额可被恶意消耗」这一代价。
2. **下载接口的拒绝报文被换成 401**：`GlobalExceptionHandler` 原本返回 `ResponseEntity`，Spring 按

   派发，而认证过滤器不处理 ERROR 派发 → 最终返回 **401「请先登录」**，真实原因（403「你不是该门户的
   管理者」）被顶掉。`smoke-portal-export.py` 的「无门户授权导出被拒」断言实测 401 时暴露。改为直接写
   JSON（core 与 query 两侧），并保留「响应已提交」的降级日志。
3. **限流抑制窗口与脚本预期不一致（行为正确、断言写错）**：「同一来源 1 分钟内重复提交同内容不累加
   计数」是刻意设计（连点两下不该算成两个人）。接口脚本最初断言计数递增，实测 `reportCount` 保持 1。

   不为了跑得快去注入可配置时钟，因为那样「真实库里到底怎么算」就永远没人验证。

### 17.4 本批抓到的真实问题

1. **预览走 POST 被 CSRF 拒绝**（首轮自检 37 项里有 25 项失败，全部是 `403 无权执行该操作`）。
   平台的 CSRF 令牌是**一次性**的：校验通过后立即失效。让一次「看一眼会得到什么」的读操作去消耗
   写令牌，会让读者紧接着点下载时莫名收到 403。改为 GET 后两个入口同形，也让 curl 与脚本可以
   不带会话核对内容。**这条只有把请求真的打出去才会暴露**——单元测试用 Mock 直接调服务方法，
   永远看不到安全过滤链。
2. **同时勾选「已合并的原记录」与「幸存记录」，文件里出现两份相同引用**。原记录会被重定向到终点实体，
   两条 id 解析成同一条成果；首版按 id 去重（`normalizeIds`）挡不住这种情况。改为按**解析后的实体**
   分组去重，并优先保留未经重定向的那条作为条目。首版按出现顺序去重，结果把「幸存的记录」记成重复项，
   读起来是「那条活着的被跳过了」——语义上说不通。
3. **浏览器脚本首轮 11/13**：两处是脚本自身的问题，不是产品缺陷。① 断言 BibTeX 预览以 `@article{`
   开头，但默认检索首屏第一条是项目类成果，条目类型按设计是 `@misc`（只有论文用 `@article`）；
   ② 未登录时 `/api/v1/auth/me` 返回 401 被记成故障——这条在 `cn-shoot.mjs` 的白名单里早就有，
   新脚本漏抄。修正后 13/13，且预览正文与下载字节逐字一致（687 字节）。

### 19.5 本批抓到的真实问题（不是夹具问题）

1. **`URI.create` 不接受裸竖线**。OpenAlex 批量查询要把多个 DOI 拼进 `filter=doi:a|b|c`，
   直接带 `|` 在发请求之前就抛 `Illegal character in query`，接口回 400、日志只有一行「请求格式不合法」。
   必须写 `%7C`。这条单测抓不到（mock 的是 fetcher 之后的层），只有真发请求才暴露。
2. **首轮补水被来源配额整轮挡住**。`X-RateLimit-Remaining` 实测 6（阈值 10），OpenAlex 直接不可用，
   并要求等十几小时（`Retry-After≈65000`）。若把 429 记成「抓取失败」，这批成果会被反复重试、反复烧配额。
   改为 AUTO 模式：额度不足或 429 时整轮改走 Crossref 重取同一批，并把「来源查不到」单记 `NOT_FOUND`、不再进待补清单。
3. **`useAsync` 不会自动执行**。详情页加了面板却一直空白，不是报错也不是 404——`onMounted` 里忘了 `run()`，
   请求压根没发。浏览器断言（20 秒等不到面板）比接口自检更早发现这一点。
4. **Mockito 后设先赢**。用例里的 `anyString()` 兜底桩盖掉了 `setUp` 里的精确桩，三条用例的 mock 零交互。
   兜底桩移到 `setUp` 并标 `lenient()`，注释写明原因。
5. **成果自助提交的批准建档绕过了「无标识公开需人工确认」这条红线**（本轮跑全量接口自检时由
   `smoke-redlines.py` 报出：`FAIL 没有「无稳定标识且未经人工确认」的公开论文 -> 8`）。逐条查这 8 条，
   全部是审核通过后直接写 `PUBLIC/EFFECTIVE` 的提交成果：决定是人做的，但平台里唯一记录这次确认的
   动作 `ACHIEVEMENT_PUBLISH_CONFIRMED` 只在治理端「确认发布」里写过，审核通过路径没写。
   修法两条：①`SubmissionService#approve` 现在会登记 DOI（此前连 DOI 都不进标识注册表，既让红线核对
   把它算成无标识，也让引用网络找不到它）并补写这条审计，理由取裁决说明；②历史数据由 `V17` 迁移回填，
   操作者／时间／理由全部取自该提交件已有的 `SUBMISSION_APPROVED` 审计，理由末尾标注「依据审计回填」，
   不新造任何一个决定。修完 `smoke-redlines.py` 24/24，`smoke-submission.py` 45/45。
   **这条是本轮唯一一处真实业务缺陷，也是「自检脚本不是摆设」的证据：单元测试、浏览器断言都不会去查审计表。**

### 20.5 本批抓到的真实缺陷

**管理端的两个只读接口没有鉴权。** `GET /api/v1/admin/core/integrity-notices` 与
`GET /api/v1/admin/core/achievements/{id}/integrity-notices` 在普通用户会话下返回 **200**，
且返回体里含 `recordedBy`（登记账号）与完整声明列表。原因是写路径（登记／撤销）都调了
`Capabilities.require`，读路径直接把 service 的查询结果返回。

1. **批量导入真实路径必 500**：`dryRun` 正常、真实导入 `IllegalTransactionStateException: No existing

2. **`cleanLatex` 三个断言同时红**：`{Protein}`、`{Alpha, Beta}` 的花括号没被剥掉，`Caf{\'e}` 变成
   `Cafe`（重音丢了）。原因是重音与格式命令都靠花括号定位，而实现里顺序不当。修法：格式命令 → 数学模式 →
   转义符号 → 剥剩余花括号 → 重音，并把重音改成「基字母 + Unicode 组合附加符号 + NFC 归一化」。
   这 20 条用例是本批新写、**第一次真跑**，说明「写完没跑」与「跑过」是两回事。

3. **种子包导入的两个假失败**（21.4）：`evt_revision_counter` 撞主键是真失败；行数不一致是**计数方式错**
   （`wc -l` 数 CSV）。修法：行数改由导出会话里的 `SELECT count(*)` 回报（`CNSEED_ROWS:<表>:<n>`），
   匹配前裁剪 psql 表格输出的对齐空格；导入前 `DELETE FROM evt_revision_counter` 再覆盖。

4. **匿名页面调了需要登录的接口**：学者档案页无条件请求 `/account/favorites/{id}`，匿名访客每次打开
   档案都在控制台留一条 401，浏览器断言「全程无 4xx」因此转红。修法：匿名走
   `/public/scholars/{id}/favorite-count` 只读数量，登录后才读带 `favorited` 的状态。

## 22 第十三批补丁：注销与保留期的闭环（2026-10-19 收尾）

第十三批交付时留了两个「功能在、但不会自己发生」的缺口。本节记录补齐与实测。

### 22.1 冷静期届满不会自动执行（真缺口）

交付时只有 `AdminClosureController.decide` 一条执行路径。用户申请注销后，若管理员不动手，
账号会一直停在 ACTIVE——而页面写的是「7 天后生效」。**这是承诺与实现不一致**，不是体验问题。

补法：`ClosureMapper.listDue` 取 `status='PENDING' AND now() >= effective_at`，
`AccountClosureService.executeDue` 逐条独立事务执行（一条失败不连累同批），
`AccountClosureSweeper` 每小时调度一次（`cn.closure.sweep-*` 可配）。
执行动作与人工裁决共用 `disableAccountForClosure`，不存在第二套停用逻辑；
`decided_by` 留空、审计主体写 `SYSTEM`，不伪造管理员账号。

管理员的否决权仍在冷静期内：想驳回必须在 `effective_at` 之前点，过期即执行。

### 22.2 会话撤销表清理是死代码（真缺口）

`AuthService.purgeRevocations` 有实现、有 SQL、有注释，**全仓零调用点**。这张表在每次鉴权时被查，
而每次改口令、重置、封禁都会写一行。补 `RetentionSweeper` 每天跑一次（默认保留 30 天，
可配 `cn.identity.revocation-retention-days`）。

### 22.4 这一节最值得记的排查教训

一度以为「`@Scheduled` 没生效」：日志停在启动那一刻、库里那条已到期申请始终 PENDING。
实际是**进程早已被沙箱回收**（`service.sh stop core` 显示「未在运行」），而 `health` 曾返回 UP
只是回收前的残留。为了让这类问题不再靠猜，做了三件事：

1. `sweep()` 首次执行打一行 INFO（扫描 0 条时按设计不打日志，否则无法区分「没调度」与「没活干」）。
2. 显式配置 `spring.task.scheduling.pool.size: 4`。Spring 默认单线程，本服务已有 outbox 投递
   （fixedDelay 800ms）与本次两个维护任务，共用单线程时慢任务会让其余任务排队且无日志。
3. 内部维护端点 `POST /internal/v1/maintenance/closure-sweep`（服务令牌保护），
   与定时任务同一段逻辑，供运维手工确认，不需要等一小时。

另外修了一个自己引入的配置事故：为加 `spring.task.scheduling` 又写了一个顶层 `spring:`，
而文件里已有第 9 行那个。重复顶层键不报错，后者覆盖前者，`datasource`/`flyway`/`redis` 全部静默丢失。
已在 `PITFALLS-OPS.md` 记下「插新顶层键前先 grep 顶层键」。
