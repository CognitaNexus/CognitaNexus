## 2 记录原则

1. **只记真实发生的事。** 每一项都要能指到仓库里的文件、命令或输出。没有执行过的测试、覆盖率、压测一律写「未执行」。
2. **修正案例必须写出「怎么发现的」。** 只写「AI 写错了、人改对了」没有价值；要写出发现它的那条断言、那次运行、那个数字。
3. **包含对 AI 不利的记录。** 能力边界与失效模式只写优点等于没写。[审查记录](审查记录-AI审查与人工审查对比.md) 里「9 个真实缺陷中 AI 审查独立发现 0 个」就是这条原则的产物。
4. **不写无法核对的数量。** 「使用 N 次」这类没有埋点的数字不写；有提交与文件可核对的产出才登记。
5. **未达项与已达项分开写。** 覆盖率 8 个受门禁包全部 ≥80% 是事实；`query/discovery` 未纳入门禁、实测 13.50% 也是事实，两者必须同时出现。
6. 时间以报告日期为准，均来自本仓库现有提交与运行记录。

## 3 怎么复核

| 想核对什么 | 命令或路径 |
| --- | --- |
| 单元测试数量与结果 | `./mvnw -B -ntp verify -Dspotless.check.skip=true`，看各模块 `Tests run` 汇总 |
| 覆盖率与门禁是否真的在拦 | `bash ops/verify-coverage-gates.sh --skip-build`（含阈值 1.01 反证） |
| 某一约束的实现位置 | [SPEC-代码对应关系表](SPEC-代码对应关系表.md) 的「实现位置」列 |
| 某个缺陷是否真修过 | [AI生成-人工修正案例](AI生成-人工修正案例.md) 每例给出的提交号与文件，配合 `git show` |
| 提示词模板现状 | [prompts/](../../prompts/) 各文件头的版本与「硬性要求」「禁止项」 |
| 接口与端到端行为 | `tests/api/` 下各脚本（需先起整栈：`bash ops/local/stack.sh`） |
