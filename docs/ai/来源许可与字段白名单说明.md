# 来源许可与字段白名单说明（WB-10）

编写时间：2026-10-17。状态：待评审。本文只描述代码当前事实与本次验证结果，不含未执行的结论。

## 1. 三个不同的控制对象

平台里「能不能采」「能不能存」「能不能公开」是三件事，混成一个开关会导致两种相反的错误：把可采集当成可公开，或者把不可公开连采集一起停掉。三者的控制点如下。

| 控制对象 | 现有承载 | 生效位置 | 当前事实 |
| --- | --- | --- | --- |
| 许可允许采集 | `raw_source_config.license_scope`（如 `CC-BY-4.0`、`CC0`） | 人工在来源登记时填写；`SourceAdminService.create` 只校验非空 | 仅作登记与展示，采集执行链路未据此判断「该来源是否允许抓取」 |
| 许可允许持久化 | `raw_source_config.allowed_fields`（JSON 数组） | 采集侧 `ImportService` 与四个适配器按白名单裁剪；core 侧 `SourceIntakeService.ingestOne` 在解析前再过滤一次 | 两侧都已生效。空白名单表示不额外限制（既有语义） |
| 许可允许公开 | `core_achievement.visibility` + `effective_status` + `data_nature`，由 `AutoPublishPolicy` 判定 | 入库建实体时一律 `RESTRICTED` + `PENDING_GOVERNANCE`，满足自动发布判据才转 `PUBLIC`/`EFFECTIVE` | **尚未与 `license_scope` 联动**：一个 `license_scope` 标为不可再分发的来源，其成果仍可能通过自动发布判据进入公开目录。这是已知缺口，未在本次授权范围内改动 |

缺口说明：上表第三行与第二行之间没有约束关系。要补上，需要先确定「哪些 `license_scope` 取值允许公开」，这属于许可策略评审，不是代码可以自行决定的事。本次不改默认行为，只把事实写清。

## 2. 白名单为什么必须在解析之前生效（WB-10 的缺陷与修复）

改动前的顺序是：先用 `input.payload()` 构造 `NormalizedRecord`，再计算 `filtered` 并只把 `filtered` 存进 `raw_source_record`。后果是原始报文干净了，而规范化成果、类型扩展、贡献、领域读的都是过滤前的记录。表现形式最容易被误判：**看原始存储会得出「白名单已生效」的结论**，实际上摘要、DOI 甚至作者都进了规范表。

修复后的顺序：

```text
input.payload()
  → applyFieldWhitelist(payload, config.allowedFields())
  → NormalizedRecord.of(filtered)
  → 规范成果 / 类型扩展 / 标识注册 / 贡献挂接 / 领域归属
  → raw_source_record.payload 写 filtered
```

验证用例 `SourceFieldWhitelistIT.whitelistAppliesBeyondRawJson` 把禁入标记同时放进摘要、DOI、刊物与作者，逐个出口断言：

- 出口一 原始存储 `raw_source_record.payload`：不含标记（改动前这里本来就干净，单看它会把缺陷判成已修）；
- 出口二 论文扩展表 `core_paper` 的 `abstract_text`／`doi_norm`／`venue`：均为 NULL；
- 出口三 标识注册表 `core_identifier_registry`：该实体零行；
- 出口四 贡献表 `core_contribution`：该成果零行。

修复前的实测输出：第二条断言失败（`expected: null but was: "…白色标记…"`），构建失败；修复后四条全通过。

## 3. 配置版本变化与重放的实际行为

`raw_source_config` 有 `config_version` 列，但入库判定**不按记录上的版本回看**：每次接收都读当前配置。因此配置变化对入库的影响只有一条规则——**只对之后到达的记录生效**。`SourceFieldWhitelistIT.narrowingWhitelistAffectsOnlySubsequentIntake` 实测了三件事：

1. 版本 1（不限制）入库的记录，摘要进了 `core_paper.abstract_text`；
2. 收紧到 `["kind","title","publicationYear"]`（`config_version` 改为 2）后，重放同一条原始记录：回执为 `DUPLICATE`，**不重跑规范化**，`abstract_text` 仍是版本 1 写入的值；
3. 版本 2 之后的新记录：`abstract_text` 为 NULL，说明收紧立即生效。

由此得到两条必须写明的事实，不能含糊：

- **重放不能用来「清洗」历史字段。** 重放的输入是已过滤的暂存报文，规范化只重跑存储的这份内容，不会按新白名单重新裁剪已入库的派生字段。
- **放宽白名单无法恢复被丢弃的字段。** 被裁掉的键在首次入库时就没有落盘，没有任何副本可以回溯。唯一可行的补救是重新采集该条记录（新的 `sourceRecordId` 或新的内容指纹），不是重放。

## 4. 现有违规字段的处理（本次不动库）

对于按旧顺序已入库的历史字段，本次**没有**执行任何清理或迁移：清库与数据迁移属于受控操作，需单独授权并留痕，本次建议不授权直接改库。

可执行的只读诊断（在约定验证窗口内运行，不写库）：

```sql
-- 找出可能违反当前白名单的历史字段：实体已存在的字段，其对应键不在来源白名单内
SELECT a.id AS achievement_id,
       s.source_code,
       c.allowed_fields,
       p.doi_norm,
       p.venue,
       (p.abstract_text IS NOT NULL) AS has_abstract
FROM core_achievement a
JOIN core_achievement_source aas ON aas.achievement_id = a.id
JOIN raw_source_config c       ON c.id = aas.source_id
JOIN core_paper p              ON p.achievement_id = a.id
JOIN (SELECT id, source_code FROM raw_source_config) s ON s.id = c.id
WHERE c.allowed_fields <> '[]'::jsonb
  AND (
        (p.doi_norm IS NOT NULL
         AND NOT c.allowed_fields ? 'doi')
     OR (p.venue IS NOT NULL
         AND NOT c.allowed_fields ? 'venue')
     OR (p.abstract_text IS NOT NULL
         AND NOT c.allowed_fields ? 'abstractText')
      )
ORDER BY a.id;
```

该查询只回答「哪些历史行可能违反当前白名单」，不等于结论：一份记录可能有多个来源，某字段也可能来自白名单允许的那个来源。真正定性需要逐条比对 `core_field_provenance.source_record_id` 指向的原始报文。
