## C-01 治理读接口没有能力校验：登录即等于授权

**现象。** 候选工作台、合并台账、合并预览三个读接口对任何已登录账号开放；合并执行业务接口同样只有登录校验。普通用户账号可以直接读到两端成果标题与相似度，并触发合并。

**发现方式。** 端到端测试写「普通用户越权」反例时暴露：用普通账号请求治理读接口返回 200。同一批断言里，账号列表接口对普通用户返回 403，两者并列出现，「有的接口拦了、有的没拦」一眼可辨。这条在 `tests/api/smoke-contract.py` 与 core 自检的越权段落里可复核。

**初版错在哪。** 治理模块的读路径复用了平台层的「已登录」拦截器就结束，写路径才逐个补 `Capabilities.require`。AI 的推理是「读比写安全」，于是读接口只做了认证。问题在于治理数据本身是敏感数据：候选两端是尚未决定的同实体判断，读到它等于提前知道治理结论。

**人工怎么判。** 判据是《工程协作与AI协作规范》与需求红线的原文：前端隐藏入口不构成授权，授权必须服务端校验；治理数据的可见性属于业务规则而不是体验细节。因此读接口同样需要 `governance:manage`。

**修法。** 16 个方法补 `Capabilities.require(actor, CAP_GOVERNANCE_MANAGE)`，覆盖工作台列表、分档计数、候选详情、台账、合并预览、改判、驳回与合并执行。

**回归证据。** 普通用户访问治理读接口与非治理账号调用合并均被拒绝；core 自检与红线脚本里对应条目通过（`tests/api/smoke-redlines.py` 24 项含越权读治理数据）。

**教训。** 「登录」不等于「授权」。审查时不能只看「这个方法里有没有鉴权代码」，要看「同一资源的全部出口是否用同一个判据」。单文件审查看不出这种跨方法的不一致。

## C-02 合并重定向绕过公开资格：旧链接能打开仍受限的实体

**现象。** 成果被合并后，用被合并方的旧标识请求详情，服务端沿 `mergedIntoId` 跳到幸存实体并返回。但跳转这一步在公开资格校验之前发生，且返回的是 `baseView` 空壳视图。结果是：拿到一个旧标识，就能确认某个幸存实体存在，即便它仍处于 `PENDING_GOVERNANCE` 或 `RESTRICTED`；页面还只显示半张卡片。

**发现方式。** 合并后遗症自检（`tests/api/smoke-merge-aftermath.py`，8 项）走「旧标识 → 终点」这条链，断言终点必须是公开可读的实体；构造一个受限幸存实体时，旧标识仍返回 200 且字段残缺。

**初版错在哪。** 初版把「重定向」当成 HTTP 语义的实现细节，先跳转再组装；资格校验写在「按标识直接打开」那条分支里，重定向分支绕过了它。空壳视图则是因为重定向分支只调了 `baseView` 而没有走完整详情装配。两个错误叠加：既泄露存在性，又不给可用信息。

**人工怎么判。** 判据是红线「待核验/争议/已排除的关系不得显示为确定合作」的同一原则——不可见对象的任何信息都不应通过旁路泄露；同时「不存在」与「不可见」对外必须不可区分，避免用状态码探测。

**修法。** 顺序改为：先解析合并链终点（`resolveSurvivorId`，多级合并一次跳到最终实体）→ 对终点做可见性与生效状态校验（不通过一律 404）→ 用 `detailViewOf` 组装完整详情 → 最后追加 `redirectedFrom` / `redirectNote` 两个说明字段。响应与直接打开终点同构。

**回归证据。** `smoke-merge-aftermath.py` 断言旧标识跳到终点、被并走的标题从检索中消失、台账留快照；详情响应字段集与直接打开一致。

**教训。** 任何「先跳转再校验」的写法都要问一句：跳转的目标是谁决定的。重定向不是展示细节，它本身就是一次访问，必须走同一套资格判定。

## C-03 撤销发布后投影残留：重建结果与增量结果对不上

**现象。** 增量路径与全量重建路径对同一段历史给出两个不同的图规模：增量累积出的参与关系与领域条目 37492，全量重建只有 37388。差的 104 条是「已撤销发布的成果」留下的关系边与领域归属。

**发现方式。** 投影一致性自检（`tests/api/smoke-projection-consistency.py`，15 项）真触发一次全量重建，比对 300 条成果的逐字段指纹并核对边数。两条路径的数字并列打印，差值不解释就无法通过。

**初版错在哪。** `ProjectionApplier` 处理增量事件时「按载荷写」：载荷里带什么就写什么。撤销发布的事件载荷仍带着参与关系与领域（它们描述的是权威侧的事实，不因下架而消失），于是投影侧保留了边；而全量重建只导公开快照，不可见成果根本不进快照，边自然没有。两个出口对「不可见成果的关联数据」采用了不同口径。

**人工怎么判。** 判据不是「哪个数字对」，而是「哪一个与公开读路径的口径一致」：检索与网络都不应看到不可见成果的边，因此增量路径错。这也符合红线——模拟或不可见数据不得进入默认现实视图。

**修法。** 不可见成果在投影侧写入空的关系与领域集合，并显式删除既有边，使增量路径与重建路径收敛到同一结果。

**回归证据。** `smoke-projection-consistency.py` 重建后比对通过，outbox 无积压、三水位一致、inbox 无重复。

**教训。** 「重建结果 = 增量结果」必须有一条真会跑重建的断言。只在增量路径上测试，这类偏差永远不会出现——它是两条路径的分歧，单看任何一条都正确。

## C-04 JDBC 通用执行计划导致 14 倍退化：18ms 变 262ms

**现象。** 领域洞察的单次查询在同一连接上「前几次很快、第 6 次开始变慢」：18ms → 262ms。冷启动后重跑，重复同样的节奏。

**发现方式。** 性能基线脚本（`tests/api/smoke-perf.py`，17 项）对每条读链路跑 30 轮并打印 P50/P95/P99。第一次跑就出现「P50 正常、P95 与最大值差一个数量级」，这个形状说明不是数据量问题，而是同一语句在不同执行次数上走了不同计划。

**初版错在哪。** 不是代码写错，是配置缺省。PostgreSQL 的 `plan_cache_mode` 默认 `auto`：同一 PreparedStatement 执行到第 6 次时切到通用计划，参数不再参与代价估算，选择性被抹平，索引失效。代码层面完全看不出问题——SQL 是对的，索引也在，只是没用上。

**人工怎么判。** 判据是「根因必须解释全部现象」：`auto` 的第 6 次阈值正好解释了「前 5 次快、第 6 次慢」，以及为什么冷启动重跑会重演。另一条判据是「配置项要验证真的生效」：改动后必须看到数字变化，而不是「应该会好」。

**修法。** 三个服务的 Hikari 连接池统一加 `connection-init-sql: SET plan_cache_mode = force_custom_plan`。修复后同一脚本测得领域洞察链路 5111ms → 640ms，合作网络 2 跳 7432ms → 787ms（同一次运行的对照，非并发压测）。

**回归证据。** `smoke-perf.py` 复跑，各链路 P95 回落且不再出现「首轮快、后轮跳」的形状。

**教训。** 性能缺陷不一定是代码造成的。凡是「同一语句、不同次数、不同耗时」的形状，先怀疑执行计划，再怀疑索引与 SQL。同时这条也说明：不做冷启动 + 多轮的测量，这类退化在单次手工点页面时看不见。

## C-05 行构造器写法的 `count(DISTINCT (a,b))`：比子查询慢 3 倍

**现象。** 合作网络里「不同学者对的数量」那条统计，617ms；改成「子查询 + 两列 DISTINCT」后 218ms，同一数据、同一连接、同一索引。

**发现方式。** 与 C-04 同一次性能基线里逐条对比：网络相关三条链路中，其中一条的耗时与它的结果规模不成比例（返回 1 个数字，却比返回整页数据的链路还慢）。

**初版错在哪。** `count(DISTINCT (a, b))` 在语义上完全正确，读起来也比子查询短，AI 按「等价改写」选了它。但行构造器让 PostgreSQL 无法把去重下推到索引扫描，只能先构造行再排序去重。

**人工怎么判。** 判据是「同一语义的两种写法在真实数据上量一次」。这类选择不能靠读代码裁决，必须有数字。

**修法。** 改成子查询两列 `DISTINCT`，并在 SQL 注释里写明两种写法在本库规模下的实测差距，避免后来的人「简化」回去。

**回归证据。** `smoke-perf.py` 中该链路耗时回到与结果规模相称的区间；网络链路整体 P95 见 C-04 的对照数字。

**教训。** 语义等价的写法不等于执行等价。凡是 AI 主动「简化」的 SQL，都要在真实数据上量一次；注释里要写清为什么保留看起来更啰嗦的写法，否则下一次重构会把它改回去。

## C-06 `?size=abc` 被兜底成 500：三个服务的错误语义不一致

**现象。** 请求 `?size=abc`（非法整数参数），core 返回 400 与统一错误码，query 与 ingestion 返回 500「服务器内部错误」。

**发现方式。** 契约自检（`tests/api/smoke-contract.py`，12 项）对三个服务逐一发同一组非法参数，断言「同一个错误在三个服务上语义一致」。三个服务的行为并列打印，差异直接可见。

**初版错在哪。** 三个服务的 `GlobalExceptionHandler` 不是一次写成的。core 侧遇到 `MethodArgumentTypeMismatchException` 时映射为参数错误，后写的两个服务只处理了业务异常与兜底异常，类型转换异常落到 `Exception` 分支，变成 500。每个服务的单测都通过，因为没人测「非法类型参数」。

**人工怎么判。** 判据是编码规范里「错误码语义」一节：客户端传错参数不能计为服务端故障。500 会让监控把用户输入错误算成服务不可用，也会让前端把「提示用户改输入」误做成「重试」。

**修法。** query 与 ingestion 的异常处理器补 `MethodArgumentTypeMismatchException`，与 core 同一映射（400 + 参数错误码）。

**回归证据。** `smoke-contract.py` 的错误码矩阵三服务一致。

**教训。** 「同样的代码在三个服务里各写一遍」必然产生分叉。这类一致性只能靠跨服务的对照断言守，不能靠代码评审「看起来一样」。

## C-07 只在默认入口出现的渲染崩溃：整页永久停在「正在读取…」

**现象。** 不带关键词打开检索页，页面永远停在「正在读取…」，不报错、不白屏，控制台也没有失败请求。带关键词（例如 `q=graph`）打开则一切正常。

**发现方式。** 逐页截图脚本扩到「默认入口 + 关键交互」后出现：脚本对检索页断言「结果条目数 > 0」，无关键词那次读到 0 并且控制台有一条 `TypeError: Cannot read properties of undefined (reading 'toLocaleString')`。此前脚本一直用 `?q=graph` 进入，首条是论文（有引用量），所以这条崩溃长期不可见。

**初版错在哪。** 判断写的是 `item.citationCount !== null`。服务端三个服务都配了 `default-property-inclusion: non_null`，null 字段在序列化时整段消失，前端拿到的是 `undefined` 而不是 `null`，判断为真，随后 `undefined.toLocaleString()` 抛异常。浏览排序首屏恰好是 PROJECT 类成果（本就没有引用量与 DOI），所以只有默认入口必现。Vue 捕获渲染异常后停在最后一次成功渲染，于是页面看起来像「还在加载」。

**人工怎么判。** 判据是「先确认数据形状，再判空」：直接抓一次响应报文，看字段是否存在。这一步定死了根因是序列化策略与前端判空约定不一致，不是网络或分页问题。归属上，这是前端判空缺陷，但根因是服务端把「值未知」和「字段不存在」变成了同一件事。

**修法。** 两处同时改：前端判空同时挡 `null` 与 `undefined`，`SearchItem` 的 `doi`/`venue`/`citationCount`/`citationSource` 改为可选字段，让 `vue-tsc` 在构建期拦住新的未判空使用；后端凡要表达「未知」的地方另给永不缺失的字段（年份的 `yearKnown` + `publicationYearLabel`）。

**回归证据。** 逐页脚本改为从默认入口进入，17 条路由 0 控制台错误 / 0 失败请求；窄屏 24 次无横向溢出。

**教训。** 这是本次最值得记的一条：**测试样本的选取偏差会让缺陷长期隐形**。同一个页面，用关键词进入是对的，用默认入口进入是崩的；而脚本恰好一直用前者。凡是「默认入口」，都必须单独成一条断言，不能只测「典型路径」。

## C-08 撤销发布后没有恢复入口：一次误操作不可逆

**现象。** 成果被治理端撤销发布（`WITHDRAWN`）后，无法通过任何接口恢复到已发布状态。撤销是治理动作，但撤销本身写错了也没有反向操作。

**发现方式。** 门户自检（`tests/api/smoke-portal.py`，27 项）里写「撤销后重新确认可恢复」这条正向路径时，接口返回状态冲突。

**初版错在哪。** `confirmPublication` 的前置条件写成「当前状态必须是 `PENDING_GOVERNANCE`」，把「撤销」当成终态。AI 的推理是「撤销是最终决定」，但需求里撤销是下架动作，治理端需要能纠正自己的误操作。

**人工怎么判。** 判据是「不可逆动作必须有反向路径，除非业务明确规定不可逆」。这里没有这样的规定，且撤销影响到公开检索结果，误撤的代价由学者承担。

**修法。** 放行 `WITHDRAWN` 重新确认，保持「只有具备发布资格且未被撤销的实体走首次发布」这条原有约束不变；重新确认后重新发事件，投影按新状态修正。

**回归证据。** `smoke-portal.py` 该条通过；撤销—恢复一轮后检索结果与详情一致。

**教训。** 「状态机里有没有回头路」要在设计时逐条问。AI 很容易把一个状态当成终态，因为它看起来「像是最后一步」。

## C-09 注释声称的不变量代码没做到：一句「逐字一致」骗了两个人

**现象。** `AdminCatalogService` 的一处注释声称公开投影的「分页导出与事件载荷字段名逐字一致」。实际上两个出口由不同代码路径装配，字段集与字段名都有差异。这不影响编译与主路径，但会让后来的人按注释做假设：以为改一个出口就等于改了两个，或者以为比对脚本不需要存在。

**发现方式。** 契约自检里写「导出与事件字段集一致」的断言时，逐字段比对失败。失败的差异不是业务缺陷，而是注释描述了一个不存在的不变量——真正需要的是一条比对断言，而不是一句声明。

**人工怎么判。** 判据是「注释写的东西必须能被观察验证」。声明「一致」却不给比对方法，等于给后来的人一个无法证伪的承诺。

**修法。** 三件事一起做：字段装配收敛到唯一的 `publicProjectionView(Achievement)`，三个出口（事件载荷、分页导出、单条导出）都走它；注释改成写明「三个出口共用同一装配点」以及当年真实出过的故障（导出少两个字段，重建后 6515 条公开成果被当成非公开行）；契约脚本里保留逐字段比对，并显式列出三处允许不同的字段（`changeKind` 事件独占、`achievementId` 与 `id` 为别名、`version` 由信封承载）。

**回归证据。** `smoke-contract.py` 的字段集比对通过，且跨出口版本号同值断言通过。

**教训。** 注释是给下一个人的输入，不是给自己的总结。「这两个东西一致」这类句子，要么换成一条能跑的断言，要么说清一致的判据与例外。

## C-10 无授权下载返回 401：真实的 403 被「请先登录」顶掉

**现象。** 新增门户导出接口 `GET /api/v1/account/contributions/export`（`Content-Type: text/csv`）后，用一个已登录但不是该学者门户管理者的账号请求它，期望 `403`（「当前账号不是该学者门户的管理者」），实际拿到 `401`（「请先登录」）。用户会以为自己会话过期，反复重新登录仍然 401。

**发现方式。** 新写的 `tests/api/smoke-portal-export.py` 里有一条负向断言「已登录但无授权必须 403」。第一次跑就红，报的是状态码不符。若只写「未登录必须 401」这一条，这个缺陷不会被发现——两处看起来都像「鉴权正常工作」。

**初版错在哪。** 错在把异常处理写成了「返回一个响应实体」。`@RestControllerAdvice` 的 `@ExceptionHandler` 返回 `ResponseEntity<ApiResponse>` 时，Spring 仍按请求的 `Accept` 头挑选消息转换器来序列化这个返回值；下载接口的请求带头是 `Accept: text/csv`，没有任何转换器能把 `ApiResponse` 写成 CSV，于是抛出 `HttpMediaTypeNotAcceptableException`（406）。406 触发容器内部的 ERROR 派发，而安全过滤器链只为 REQUEST 派发注册，不处理 ERROR 派发，最终落到默认错误页/兜底逻辑，变成 401。整条链路里没有任何一环「判断错误」，每一环都在按自己的规则正确处理，错的是它们串起来的语义。

**人工怎么判。** 判据是「客户端的可见结论必须等于服务端的真实拒绝理由」。这类跨切面错配不能靠改前端文案解决，也不能只改导出接口——任何下载类接口（检索结果导出、材料下载、备份下载）都会中招，所以要改的是异常处理这一层的写法。

**修法。** core 与 query 两侧的 `GlobalExceptionHandler`，所有 `@ExceptionHandler` 从返回 `ResponseEntity` 改为返回 `void`，直接用 `ObjectMapper.writeValue(response.getOutputStream(), ApiResponse.failure(...))` 写响应体并 `flushBuffer()`；响应已提交（`response.isCommitted()`）时只记日志，不再二次写。类注释里把上面这条故障链完整写下来，避免后人「优化」回返回实体的写法。

**回归证据。** `smoke-portal-export.py` 的 401 / 403 两条断言同时通过；`smoke-contract.py` 的错误码矩阵不受影响（它用 JSON 的 `Accept`，本来就是通的）。

**教训。** 「每个组件都正确，整体语义是错的」是这一层最危险的缺陷形态。它只在特定 `Accept` 头下出现，用浏览器点页面永远看不到——因为浏览器要的是 HTML/JSON。凡是「按请求头协商输出格式」的框架能力，错误路径也必须显式声明输出格式，不能依赖协商。

## C-11 限流规则写了上限却永不生效：键里多拼了一个维度

**现象。** 公众纠错接口设计了三层防灌：来源级 5 次/10 分钟、单成果全局 20 条/24 小时、同来源 1 分钟内同内容只并入不累加。单测 `rateLimitsBySource`（来源级）与 `rateLimitsPerAchievement`（单成果级）分别断言，其中单成果那条一直失败，报的却是来源级的文案「提交过于频繁」。

**发现方式。** `mvn verify` 里新加的 `PublicCorrectionServiceTest` 红了。第一反应是「测试写错」，因为代码读起来完全正确：调 `enforceRate(perAchievementKey, 20, 24h, ...)`，键是 `"ach|" + achievementId + "|" + sourceKey`。

**初版错在哪。** 键里多拼了来源地址。于是「单成果 20 条」实际统计的是「同一来源对同一成果 20 条」——而来源级窗口是 5 次/10 分钟，永远先触发。「单成果配额」这条规则在库里存在、在配置里有常量、在测试里有名字，**但它在任何输入下都不会触发**。这不是并发或边界问题，是规则本身被另一个维度的键覆盖掉了。

**人工怎么判。** 先判「哪条规则是想要的」：单成果配额要防的是「多个来源/IP 轮流滴灌同一成果」，所以键必须是纯成果维度，不能拼来源。再判代价：一旦不拼来源，任何人只要攒够 20 次提交就能把这个成果的纠错通道堵死 24 小时。这个代价被接受，并写进常量注释——把「谁能消耗谁」讲清楚，比只写一个数字有用。

**修法。** 键改为 `"ach|" + achievementId`，上限 20 条/24 小时；测试改成「20 次不同来源全部受理，第 21 次被拒」，这样一旦有人把键改回去，用例立刻红。三层规则的职责也在注释里各自写明，避免再被合并。

**回归证据。** `PublicCorrectionServiceTest` 10 项全过；`smoke-corrections.py` 33 项全过（含真实 HTTP 下的 429 断言与「限流不占用待办配额」断言）。

**教训。** 「有上限但永不触发」比「没有上限」更糟：它让人以为已经防住了。写完任何上限/配额类规则，必须构造一次「刚好超过上限」的输入，看它真的拒绝；改配置看行为是否随之改变（同一批里 `max-backoff-seconds` 也曾被位移上限吃掉）。测试用例名里带规则名的那些，最容易被当成「已经覆盖」。

## C-12 前端自己拼引用：四个缺陷与一份把缺陷固化成预期的测试

**现象。** 详情页的「引用这条记录」面板可选 GB/T 7714 / BibTeX / RIS / APA 四种格式，复制与下载都正常。用真实库里的成果逐条比对时发现四类问题：题名含 `%` 的成果导出的 BibTeX 编译后字段残缺；未登记作者的成果导出的 entry 里 `note` 出现两次；中文作者的引用键是 `anon2026…`（回退值）；一位 `PENDING_VERIFY` 的署名者从引用里消失了。

**发现方式。** 不是测试报的——四个问题没有一个会让测试红。发现方式是拿三条真实成果（含 `%` 的题名、无作者的专利、有 `PENDING_VERIFY` 参与关系的论文）手工导出，再逐字段核对；BibTeX 那条还用 `bibtex` 编译了一次。

**初版错在哪。** 四个缺陷各自成立，根因是同一个判断：「引用是展示，展示属于前端」。

1. **`%` 未转义**。`bibValue` 只处理 `\` 与 `{}`，注释写着「& % $ # _ ^ ~ 在 .bib 正文里合法，擅自加反斜杠会让标题与原文不一致」。前半句对，`%` 例外：它在 BibTeX 里是注释起始符，行内出现即截断该行剩余内容（连同后面的 `}`），编译时报字段缺失。
2. **`note` 写两次**。无作者时先 push `note = {作者不详}`，末尾又无条件 push 出处 `note`。BibTeX 对重复字段不报错，取最后一个——占位说明被静默丢掉。
3. **引用键取「姓氏」**。`firstAuthor.trim().split(/\s+/).slice(-1)[0]` 取名字最后一段：`Zhang San` 得到 `San`，纯中文名过滤后为空落回 `anon`。注释还写着「保证同一库内不重复」。
4. **作者列表只取关系合格的学者**。`qualifiedContributors` 过滤掉 `PENDING_VERIFY` / `DISPUTED`，于是待核验的署名者被从引用里删掉。注释的理由是「署名是断言，把待核验的关系写进引用等于替来源确认了一件尚未确认的事」——这句话本身成立，但它把两件事混了：**署名是元数据事实**（来源写了几个人就是几个人），**关系状态回答的是「这位学者是否被正确匹配」**。删掉署名者不是更严谨，是让引用与原文不一致。

**人工怎么判。** 三条判断：

- 第 3 条不算缺陷而是「没做对」——姓氏提取在中英文里至少有一种会错，正确做法是不提取，用整名折叠加成果标识尾段保证唯一。
- 第 4 条按「元数据事实优先」改：署名者保留，把「归属待核验」作为**告警**给出，让读者自己决定要不要核对。删数据与标注数据之间，选标注。
- 第 1、2 条是纯 bug，无争议。

另外判了一件更大的事：**这份逻辑不该留在前端**。前端看不到 `EXCLUDED` 的关系、看不到 `author_order IS NULL`、看不到当前生效的撤稿声明——它手里没有做对所需的输入。结论是文本与告警一并挪到服务端（记入 ADR-004）。

**最值得记的一点。** 旧测试里有一条：

```ts
test('BibTeX：key 由第一作者 + 年份 + 标识尾段构成', () => {
  // 平台不能可靠切分姓与名（纪律 2），key 取第一作者最后一个空格段做启发式，
  // 中文姓名则整段保留。这里按实现的实际行为断言，防止未来静默改变格式。
  assert.ok(text.startsWith('@article{Shiping202434ef56,'))
```

注释里「不能可靠切分姓与名」是对的，紧接着却用这句话解释了「所以取最后一个空格段」——自相矛盾，而测试把 `Shiping` 这个错误结果钉成了预期。它之所以一直绿，是因为它断言的是**代码的当前行为**，不是**规范要求的行为**。

**修法。** 服务端 `CitationFormatter`（纯函数）逐个格式实现，`bibEscape` 覆盖十个语法字符并断言花括号平衡；`citeKey` 用「整名折叠 + 年份 + 题名段 + 成果标识尾段」；作者只剔 `EXCLUDED` 并给出 `AUTHOR_ORDER_UNKNOWN` / `AUTHOR_PENDING_VERIFY` / `EXCLUDED_DROPPED` 三条告警。前端缩成状态装配，只保留三个纯函数（下载前缀、告警严重度、格式回退）。

**回归证据。** `CitationFormatterTest` 17 项、`CatalogCitationServiceTest` 10 项、`PublicCitationControllerTest` 3 项、`frontend/tests/citationView.test.ts` 6 项；`smoke-citations.py` 41 项全过（真实库真服务，含撤稿前后对照与「下载正文与 JSON 文本逐字一致」）。

**教训。** 一条测试写着「按实现的实际行为断言」，它就不再是测试，而是一份变更记录。凡是注释里出现「这是启发式」「暂时这样」，就应该问一句：把它写成断言，是在保护行为，还是在保护缺陷？

## 分歧案例（WB-14 要求：同一输入、原始输出、追问、冲突点、人工裁定）


上面十二例是「代码错、测试抓住」；下面三例是**同一份输入下 AI 与人工得出不同结论**，最后以人工裁定
定稿。它们不是课后编的讨论：三例都发生在 2026-10-17 第三批（容量与恢复）工作中，原始输出可以在
`docs/ai/第三批-容量与恢复验证记录-2026-10-17.md` §4.4、§5.1 与 `reports/perf/20261017-201805/`
的 JSON 里逐条核对。模型为会话内模型 DeepSeek-V4.1-Flash，输入是同一份仓库上下文与同一批测试输出。

### D-01 回执里的 received 到底算不算重复投递

- **输入背景**：`InboxReceiver.receive` 写完数据库后返回 `BatchReceipt`，字段含义写在 note 里
  （「received 表示已持久接收」）。同一 eventId 第二次投递时唯一键拦下，落库 0 行。
- **AI 的初版输出**：`received = records.size()`（本批折叠后的条数），`duplicated = records.size() - inserted`。
  于是「投递一条已存在的重复事件」得到 `received=1, duplicated=1, applied=0`。
- **我的追问**：「这一批到底有几行被写进去了？如果 received 是 1，那 duplicates 也是 1，两个数字
  相对同一行，`received + duplicated` 又等于 2。运维读这三个数能得出什么？」
- **冲突点**：AI 的立场是「received 表示本批收到几条请求」，人的立场是「回执的 note 自己说了
  received 是已持久接收，那么重复项就不是 received」。
- **人工裁定**：改为 `received = inserted`（真正落库条数），并把字段口径写进 `BatchReceipt` 的 javadoc。
  理由是这条回执会被 core 与运维当成「收下了多少」，把没写进去的算进去，等于对外夸大接收量。
- **验证**：`ProjectionRecoveryIT.duplicateDeliveryHasSingleBusinessEffect` 先红（`expected: 0 but was: 1`），
  改后转绿；同一次运行里 4 个用例全通过。

### D-02 「积压 3 条」到底是哪一段积压

- **输入背景**：乱序抵达用例，先收到 revision=3（缺 1、2）。进度行三个水位：接收 0、见过最大 3、已发布 0。
- **AI 的初版输出**：记录里写「`highestSeenRevision=3`、`publishLag=3`，发布 `DEFERRED`」；
  代码里 `pendingRemaining = receivedRevision > publishedRevision`。
- **我的追问**：「`publishLag` 是 `received - published`，这里是 0；3 是 `highestSeen - received`。
  另外，既然库里有 3 条没投影，回执为什么回答没有积压？」
- **冲突点**：AI 把「积压」当成一个标量，任取一个差值填上；人要求区分**接收侧积压**与**发布侧积压**，
  因为两者的处置完全不同：接收侧缺口要去追投，发布侧积压要等消费者。
- **人工裁定**：① 记录拆成 `receiveLag=3` 与 `publishLag=0` 两个字段分别断言；② 回执的
  `pendingRemaining` 改用 `highestSeen > published`——原判据在缺口停摆时两边都是 0，会在最该报积压的
  时刻回答「没有积压」。
- **验证**：`ProjectionRecoveryIT.outOfOrderRevisionStallsUntilGapFilled` 先红
  （`Expecting value to be true but was false`），改后转绿；记录 §5.1.2 同时更正了首稿的错误表述。

### D-03 100 活跃用户的 P95 比 50 活跃用户低，是变快了吗

- **输入背景**：`reports/perf/20261017-201805/` 下 50 VU 与 100 VU 两份 JSON，同一套固定查询、同一台机器。
- **AI 的初版输出**：「100 VU 的 P95 反而低于 50 VU」，并在小结里倾向写成「负载上升后响应更稳定」。
- **我的追问**：「成功率是多少？失败的那些花了多久？」
- **冲突点**：AI 只比较了成功请求的 P95。100 VU 的稳态成功率是 24.9%，另有 3 848 次
  `CannotGetJdbcConnectionException`——这些请求在 5 秒连接超时处就结束了，根本没进 P95 的样本。
  在一个「大部分请求失败」的运行里，成功的少数恰恰是最幸运的那批，P95 自然好看。
- **人工裁定**：① 结论改为 **NF02 未达成**；② 因果链按证据排序：统计概览单请求 34–64 秒 →
  query 连接池（16）打满 → 连接超时成片失败 → 76 次请求被客户端取消；③ 在记录里显式写下
  「100 VU 的 P95 低于 50 VU 是失败得快，不是更快」，避免下一个人照抄这行数字。
- **验证**：`reports/perf/20261017-201805/load-100vu.json` 的 `overallSuccessRate=0.249` 与
  `steadyRps=15.41`；`pg_stat_activity` 采样 `active=16 / idle=6` 与连接池上限一致；
  服务日志里 3 848 条 `CannotGetJdbcConnectionException`。

**三例的共同点**：AI 的输出在「局部自洽」这一层都是对的（数字算得对、代码能跑、P95 确实是那个值），
错在**口径**——它回答了被问的那句话，而没有回答读这句话的人真正需要判断的事。人工的作用不是改数字，
是先把「这个数字代表什么」定下来。

## 从十二例归纳的失效模式

| 失效模式 | 表现 | 为什么 AI 容易犯 | 本仓库的防线 |
| --- | --- | --- | --- |
| 主路径正确、旁路失守 | 重定向绕过资格校验；读接口不做能力校验 | AI 按「这个功能的正常流程」组织代码，旁路不在它的流程图上 | 每个资源列出全部出口，断言逐个覆盖；跨方法一致性由脚本而非评审保证 |
| 单点正确、两路分叉 | 增量与重建结果不一致；三个服务错误语义不一致 | 一处实现只在一处被考虑，重复实现不会被自动对照 | 「两条路径必须相等」的断言（重建 vs 增量、服务间对照） |
| 等价即安全 | 行构造器 SQL、通用执行计划 | 语义等价被当成性能等价；配置缺省不在代码里 | 在真实数据上量一次；配置项改动必须看到行为变化 |
| 样本偏差 | 检索页只用 `?q=graph` 进入 | AI 选样例时倾向「典型、有内容」的输入，避开空与默认 | 默认入口单独成条；空集合、单元素、全同类数据各一条断言 |
| 用注释代替断言 | 「逐字一致」的不成立声明 | 声明不变量比写断言便宜 | 注释里的「一致/不变」必须给出可执行判据，否则删除 |
| 把终态当成事实 | 撤销不可恢复 | 状态机里「最后一格」看起来像结论 | 逐状态问「有没有回头路」；不可逆动作列出反向路径 |
| 自测即验收 | 「跑通了」被当作「做完了」 | 没有外部断言时，AI 只能用自己的输出证明自己 | 验收只认脚本输出与数字；未执行一律写「未执行」 |
