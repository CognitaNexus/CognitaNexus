## 1 为什么把提示词当源码

提示词决定产出的形状。只把代码纳入版本管理，等于把一半的实现依据留在仓库之外：换个人、换台机器，得到的东西不一样，评审也看不到「当初是怎么让 AI 干的」。本仓库的做法是每份模板都写明用途、上下文清单、验收判据与禁止项，并在文件头带版本号；结构性改动（增删章节）升版本号。

判定依据可核对：[prompts/README.md](../../prompts/README.md) 的修改约定写明了升版规则；每份模板正文内的「硬性要求」「禁止项」两节即验收判据。

**关于「使用次数」的说明。** 本仓库没有逐次记录模板调用次数的埋点，也没有把每次会话的对话框归档（对话不随仓库分发）。因此本清单不写「使用 N 次」这类无法核对的数量，只写「产出了什么、在哪个提交或文件里」。这一条本身是本清单的边界：宁可少一个数字，不留一个编的数字。

## 4 效果评估：哪一句真的改变了产出

评价标准不是「模板写得漂亮」，而是「有没有一条具体的错误因为它被拦住」。

| 模板 | 有效的地方（有实例） | 失效或代价（有实例） |
| --- | --- | --- |
| implement-feature | 「永不缺失的结论字段」这条要求在 `implement-feature.md` 中单列为硬性要求第 5 条，直接对应三服务 `non_null` 下「未知」被渲染成空白的问题；年份的 `yearKnown` / `publicationYearLabel`、合并预览的 `merged` 布尔都是按这条加的 | 「验收：成功样例 + 至少一个失败或权限反例」在前几轮常被写成「成功样例 + 一个不存在的 id」，那不是权限反例。案例 C-01（治理读接口无能力校验）说明：模板要求了反例，但如果反例选的是「不存在的 id」而不是「无该能力的登录用户」，鉴权缺失依然测不出来 |
| continue-code | 「只续写不重构」让 `GovernanceService` 在补改判逻辑时没有连带重排既有方法，diff 可逐条核对 | 「约定来自相邻代码」在相邻代码本身就错的时候会把错误复制一遍：`SearchView.vue` 的 `!== null` 判空在相邻代码里是同样写法，续写时被当成约定沿用了（案例 C-07） |
| explain-code | 「区分它做了什么与它想做什么」直接产出了 `AdminCatalogService` 注释与代码不一致的结论（案例 C-06 的同类问题） | 解释任务不产生可执行证据。解释得清楚曾被当成「已经确认没问题」用过一次，此后规范明确：解释不构成验收 |
| write-unit-tests | 「反例必须真的会失败」促使把实现改坏再跑一遍（回退验证），门禁反证脚本 `ops/verify-coverage-gates.sh` 是同一思路的产物 | 「断言方向要与实现措辞一致」是踩过一次才补进模板的：断言写「已并入」而界面写「已被并入」，把一次正确渲染报成红 |
| fix-defect | 「改动前先取基线」让性能类修复有前后两个数字（领域洞察 18ms → 262ms 的退化、修复后 5111ms → 640ms 的链路耗时），而不是只说「变快了」 | 「先给根因判断」在缺日志时容易被写成猜测。规范因此要求根因必须附「什么观察能推翻它」，否则只能记为待验假设 |
| review-diff | 分区让 AI 不替人下业务结论；格式与判空类问题在 AI 侧确实能收敛 | 分区不能替代覆盖：治理接口的 16 个方法缺能力校验，AI 审查没有报出来（案例 C-01）。单文件审查看到的是「方法体里没有鉴权」，看不到「同一个 Controller 的另 3 个方法有鉴权而它没有」这种跨方法一致性 |

## 5 维护约定

1. 模板出现结构性改动（增删章节）必须升版本号；只改措辞在原版本内更新。
2. 新增模板必须同时登记到本清单与 [prompts/README.md](../../prompts/README.md) 的文件表，否则视为未纳入资产。
3. 模板里的路径、命令、编号必须是本仓库真实存在的；模板不复制需求正文。
4. 本清单的「使用情况」只登记可核对的产出。新增一行必须有对应提交或文件，不接受「用过一次」这类说法。
