# 部署与运维手册

> 适用版本：v0.2 工程实现（三服务 + PostgreSQL 16 + 双 Redis + nginx 同源代理）。
> 本文只写**可复现的步骤与判据**，不写「应该没问题」这类结论。凡未实测的项都在第 9 节单列。

## 1. 拓扑

| 组件 | 端口（容器内） | 对外 | 作用 |
|---|---|---|---|
| web（nginx） | 80 | `CN_WEB_PORT`（默认 8080） | 静态前端 + 同源反向代理 `/core` `/query` `/ingest` |
| core-service | 8081 | 不对外 | 权威域：成果、学者、关系、来源、治理、账号、审计 |
| query-service | 8083 | 不对外 | 公开读投影：检索、统计、合作网络 |
| ingestion-service | 8082 | 不对外 | 采集、暂存、交接、任务调度 |
| postgres | 5432 | 仅开发期映射 | 三个独立库：`core_db` / `ingestion_db` / `query_db` |
| redis-session | 6379 | 仅开发期映射 | 会话（AOF 持久化） |
| redis-cache | 6380 | 仅开发期映射 | 可丢弃派生缓存（不落盘，LRU） |

三个服务**不共享数据库、不共享数据卷**，只通过 HTTP 内部端点与投递事件通信。这是刻意的：
共享库会让「谁拥有这份数据」在故障时无法回答。

## 2. 前置条件

- Docker Engine 24+ 与 Compose v2.24+（`compose.server.yaml` 用了 `!override` 标签）；
- 4 核 8 GB 起（三个 JVM + PostgreSQL）；磁盘按「库大小 × 3」预留（备份 + dump 临时文件）；
- 出网：首次构建需要拉取 Maven 依赖与基础镜像；运行期只有采集服务需要访问上游（Crossref / OpenAlex / NSF / Nobel）；
- 一个可解析的域名（nginx 走同源，不需要为三个后端各配子域）。

## 3. 首次部署

```bash
git clone <repo> && cd academicplatform
cp .env.example .env
# 必改：所有 *_PASSWORD、CN_*_SERVICE_TOKEN、CN_BOOTSTRAP_ADMIN_PASSWORD
# 建议：CN_COLLECT_USER_AGENT 填真实联系邮箱（Crossref/OpenAlex 会按 UA 限流）
docker compose -f compose.yaml -f ops/compose/compose.server.yaml up -d --build
docker compose ps
```

口令要求：

- `CN_BOOTSTRAP_ADMIN_PASSWORD` 没有默认值，compose 会直接报错退出——这是刻意的，留空等于把可写平台开放给所有人；
- owner 与 app 两组口令不能相同，否则「运行账号无 DDL 权限」这条约束名存实亡；
- `CN_QUERY_SERVICE_TOKEN` 在 core 与 query 两侧必须一致，配错的现象是事件被 403 拒收、公开水位不动，而不是启动失败。

首次启动顺序由 healthcheck 保证：PostgreSQL 健康 → 初始化脚本建角色与库 → 三个服务各自跑 Flyway → 前端起来。
`init-databases.sh` **只在数据卷为空时执行一次**；改这里的口令不会作用于已有数据卷。

## 4. 上线判据（每次部署都做）

```bash
bash ops/verify/compose-smoke.sh --up      # 构建 + 起 + 等健康 + 同源探活
```

四项判据，缺一不可：

1. `docker compose config -q` 通过（配置自洽，必填变量在位）；
2. 全部服务 `healthy`（不是 `running`——running 只说明进程没退，数据库可能还在恢复）；
3. `http://<host>:8080/` 返回 200（前端静态资源可用）；
4. `/core/actuator/health`、`/query/actuator/health`、`/ingest/actuator/health` 均返回 200（三服务与各自数据源连通）。

再手工确认两件事（脚本无法替代）：

- 用引导管理员登录，打开「待办」页，五个待办计数都能读到（读不到说明该类能力缺失，或迁移未完成）；
- 打开任意一条成果详情，能看到「来源」面板且外链可点（说明公开投影与来源引用都到位）。

## 5. 日常运维

| 场景 | 操作 |
|---|---|
| 看日志 | `docker compose logs -f core-service`（服务器覆盖配置把日志级别压到 INFO） |
| 重启单个服务 | `docker compose restart core-service`（不重建容器，卷与网络保留） |
| 优雅停机 | `docker compose down`（不删卷）；**不要** `down -v`，那会删数据卷 |
| 数据库排障 | 服务器配置不映射 5432；需要时临时 `docker compose exec postgres psql -U postgres` |
| 采集任务 | 采集台新建任务 → 执行 / 暂停 / 恢复 / 停止；失败任务可「失败重试」从检查点继续 |
| 投递积压 | 「一致性与投递」页看 pending/failed；死信可重投 |

## 6. 备份

```bash
bash ops/backup/pg-backup.sh                       # 默认走 compose 容器
bash ops/backup/pg-backup.sh --out /data/backups   # 指定父目录
CN_BACKUP_MODE=host bash ops/backup/pg-backup.sh   # 本机原生栈（需要 pg_dump 在 PATH 且给出 PGPASSWORD）
```

产物：`<out>/<时间戳>/{core_db,ingestion_db,query_db}.dump` + `manifest.txt`。
清单记录每个 dump 的大小、sha256，以及关键表的行数快照——**恢复后要拿它逐项核对**，
只核对「表存在」没有意义，迁移脚本自己就会建表。

建议频率与保留：

- 每日一次全量（三库同一时刻），保留 14 天；
- 每次 `up -d --build` 升级前额外做一次，且保留到升级验证完成；
- 备份目录不要与数据卷放在同一块磁盘。

## 7. 恢复

```bash
# 1) 先恢复到带后缀的新库并核对（默认行为，不动现有库）
bash ops/restore/pg-restore.sh --dir /data/backups/20261018-010203

# 2) 核对通过后，二选一：
#    a. 把连接串切到新库（维护窗口内改 .env 后 recreate）
#    b. 原地恢复（会删掉现有库）
bash ops/restore/pg-restore.sh --dir ... --in-place --yes-i-know
```

脚本的安全默认，逐条都有理由：

- **默认不覆盖**：恢复到 `<db>_restore_<时间>` 新库。dump 坏了也不会把在服务的库删掉；
- **行数核对**：与 `manifest.txt` 不一致就退出码 4，不打印「恢复完成」；
- **覆盖要两个开关**：`--in-place` 与 `--yes-i-know` 同时给出才执行。

恢复后仍需人工确认：登录可用（会话 Redis 是**另一份**状态，DB 恢复不会带回登录态）、
公开检索能出数（query 投影与公开水位一致）、采集任务未被重复领取。

## 8. 升级

1. 备份（第 6 节）；
2. `git pull` → `docker compose -f compose.yaml -f ops/compose/compose.server.yaml up -d --build`；
3. Flyway 在服务启动时**前向迁移**，无自动回滚。因此：
   - 迁移必须是「加列/加表/加索引」这类向后兼容动作；破坏性变更要拆成两步（先停用、再删除）；
   - 回滚代码不等于回滚数据库：旧版本代码要能读新 schema，做不到就只能恢复备份；
4. 升级后按第 4 节跑一遍判据。

## 9. 已知限制（未实测或未实现，验收时不要当作已具备）

| 项 | 现状 | 影响 |
|---|---|---|
| NF02 性能目标（P95 ≤ 2s） | **未达标**：统计概览在 100 VU 下曾出现 34–64s、连接池打满 | 演示与小规模可用；高并发需先做查询侧物化/缓存，不能靠加机器掩盖 |
| NF05 传播目标（≤60s） | 机制具备（公开水位 + 屏障），**未做计时实测** | 不能声称已达标 |
| 容器化部署 | compose 配置与构建脚本已具备，是否在本机/服务器实测见 `ops/verify/compose-smoke.sh` 的运行记录 | 未跑通过就不能说「已在服务器部署」 |
| 单实例 | 三服务均按单副本配置；采集有租约可多实例，core 的定时任务未做分布式锁 | 水平扩容前要先确认定时任务不会重复执行 |
| 反向代理与 TLS | nginx 只做同源代理，**未配置证书**；TLS 与 HSTS 需在上层（SLB/网关）终止 | 直接暴露 80 端口时流量是明文 |
| 证据文件 | 存放在 `claim-evidence` 卷，与数据库**不同步备份** | 恢复数据库后，证据文件需单独从卷快照恢复，否则出现「有记录无文件」 |
| 监控告警 | 只有 `/actuator/health`，无指标采集与告警规则 | 故障发现依赖人工查看 |

## 10. 故障处置

| 症状 | 先查 | 常见原因与处理 |
|---|---|---|
| 前端 502 | `docker compose ps`；`logs web` | 后端未 healthy；nginx 启动早于后端时容器会重启，等 healthcheck |
| 检索无结果但库里有数据 | 「一致性与投递」页的公开水位 | query 未追平水位 → 看 outbox 是否有 failed；死信可重投 |
| 登录后立刻掉线 | `redis-session` 健康与磁盘 | 会话 AOF 写失败；容量满时 Redis 会拒绝写 |
| 采集任务一直不跑 | 任务详情：`nextAttemptAt`、`lastError` | 正在退避（正常），或来源许可未批准，或本地配置版本与核心不一致（需「从核心同步」） |
| 撤权后仍有成果公开 | 撤权作业状态与 `residualCount` | 作业中断（FAILED）→ 调续跑；残留为 0 才算完成 |
| 备份恢复后行数不一致 | `manifest.txt` 的 `rows` 行 | dump 不完整或恢复到错库；不要继续，回到第 7 节重做 |
