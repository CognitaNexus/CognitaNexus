# 模板：缺陷修复（调试自愈）

| 项目 | 内容 |
| --- | --- |
| 版本 | V0.2，2026-10-17 |
| 任务类型 | 调试自愈／代码修复 |
| 适用 | 有可复现现象、有真实日志或响应证据的缺陷 |

## 模板正文

```text
现象：<谁在什么操作下看到了什么；包含原样的错误信息/响应片段>
复现：<命令与参数；复现是偶发还是必现；环境（哪个服务、哪个端口、哪条数据）>
已有证据：<日志行、SQL 结果、接口响应、截图路径>
排除项：<已经验证不是原因的东西，以及是怎么排除的>
要求：
  1. 先给出根因判断，并说明这个判断能被什么观察推翻；
  2. 改动限于修复该根因所需的最小范围；
  3. 说明这次修复会不会改变既有数据或契约；会的话先停下。
验收：<复现步骤变成什么结果>；<同时要被证明没有破坏的相邻行为>
禁止：把失败改成空结果、放宽断言、扩大捕获范围、加 try-catch 吞掉异常。
```

## 硬性要求

1. **没有复现就没有修复**。本仓库踩过：把「抓取失败无退避」当成「任务太多」，如果直接去加限流，问题会换个样子出现。
2. **根因要能解释全部现象**。只解释一半的根因，剩下的会在改完之后继续出现。
3. **改动前先取基线**。修之前跑一次真实自检并记录数字，改完再跑一次，用两次数值的差说明修好了；只报「改完能跑」说明不了任何事。
4. **配置项要验证真的生效**。本仓库真实案例：退避的位移上限写成了 `1L << min(attempt - 1, 6)`，最大退避被固定为 64 秒，配置项 `max-backoff-seconds`（默认 300）永远不生效——代码看着对，参数却不生效，这类缺陷只能靠「改配置看行为是否变化」发现。
5. **修完补一条会红的用例**：把修复回退掉，新加的用例必须失败。

## 常见失效模式（本仓库实测）

| 失效模式 | 表现 | 应对 |
| --- | --- | --- |
| 只在表层消音 | 报错消失但数据不对 | 核对最终数据，不核对「有没有报错」 |
| 只在正常路径验证 | 自检全绿，反例仍失效 | 反例与正常路径同时断言 |
| 把快照当现状 | 用登记时的证据渲染当前状态，显示「生效」实际已撤回 | 判断依据必须实时读取 |
| 静默空集合通过 | 门禁/断言匹配到空集合，一律判通过 | 用反证脚本确认门禁会红 |
