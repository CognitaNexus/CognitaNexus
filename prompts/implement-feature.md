# 模板：项目级功能实现

| 项目 | 内容 |
| --- | --- |
| 版本 | V0.2，2026-10-17 |
| 任务类型 | 项目级代码生成（跨层：迁移 → 领域 → 应用 → 接口 → 前端 → 测试） |
| 适用 | 新增一项可被验收的功能；不适用于改一行配置这类局部编辑 |

## 模板正文

```text
目标：<一个具体用户行为或缺陷，关联 FR / AC-IMPL 编号>
依据：架构设计说明书 <版本/小节>、编码规范 <版本/小节>、核心 SPEC <条款>、<相关 OpenAPI/事件 schema>
语义约束：<这条功能不能被牺牲掉的红线，逐条列出>
范围：允许修改的服务/模块/文件；本任务不改变的边界（不改的表、不改的口径）
输入输出：请求、结果、错误码、权限、幂等、事务边界、是否发事件、数据性质（真实/模拟/混合）
现状证据：<相关文件路径与行号；当前行为是什么，为什么不够>
验收：成功样例 + 至少一个失败或权限反例；需要真实执行的命令（构建/测试/自检脚本）
检查点：<本任务里哪些动作不可逆、需要先停下确认>
完成报告：改动摘要、测试命令与结果、未执行项、剩余问题
```

## 硬性要求

1. **先有规范再写代码**：没有对应 SPEC/AC 编号的功能不实现，先登记待确认问题。
2. **先看现状**：改变行为前必须能说出当前行为是什么。凭想象改出来的「修复」是最难查的一类缺陷。
3. **迁移只增不改**：新增 Flyway 版本号，不改已发布的迁移文件；约束变更要先核对既有数据是否仍合法。
4. **失败方向要明确**：判断不了的时候必须 fail-closed（不放行、不合并、不显示为确定）。
5. **永不缺失的结论字段**：凡是「未知／不存在」本身要被读到的信息，除可空字段外必须另给一个永不缺失的字段（布尔或标签）。三个服务全局 `non_null`，null 字段会从响应里消失。

## 禁止项

- 为了通过类型检查加 `any`、无意义强转或关闭 strict。
- 为了通过测试删断言、改期望迎合实现、全 mock 数据库事务。
- 为了联调关闭认证/CSRF、信任客户端 role、放开 CORS。
- 改动 FR/AC 语义、降低数据规模、跳过证据或混入模拟数据。
- 声称未运行的构建、测试或覆盖率已经通过。
