# 模板：单元测试生成

| 项目 | 内容 |
| --- | --- |
| 版本 | V0.2，2026-10-17 |
| 任务类型 | 单元测试（补用例、补边界、补反例） |
| 适用 | 核心模块（清洗规则、消歧算法、检索排序、统计计算）与治理裁决逻辑 |

## 模板正文

```text
被测目标：<类与方法，含行号>
被测行为（用业务语言描述，不是复述代码）：
  - 正常路径：<输入 → 期望的对外可观察结果>
  - 反例 1：<边界或非法输入 → 期望的失败方式（错误码/异常类型/不写库）>
  - 反例 2：<并发或重复调用 → 期望的幂等行为>
依赖处理：只 mock 出站端口（仓储/事件/审计），业务判定逻辑必须真实执行。
断言要求：断言对外可观察结果（返回值、抛出的错误码、对 mock 的调用），不断言内部实现细节。
命名要求：@DisplayName 用中文写「这条用例守住的是什么」，不写「测试方法 X」。
禁止：为了让用例变绿而放宽断言；用 verifyNoInteractions 代替真实断言；复制粘贴同一断言换个变量名。
```

## 硬性要求

1. **每条用例要能说出它守的是哪条规则**。说不出规则的用例是覆盖率装饰品。
2. **反例必须真的会失败**：写完先自己反推一次——把实现改坏，这条用例会不会红？不会红就说明断言没落到行为上。
3. **断言方向要与实现措辞一致**。本仓库出现过一次真实反例：界面提示写的是「已被并入」，断言核对的是「已并入」（少一个「被」），断言形近而不等，于是把一次正确的渲染报成红。断言写错方向与漏写断言一样有害——它训练人把红当成噪音。
4. **覆盖的是分支，不是行**。治理逻辑里的 fail-closed 分支、并发冲突分支、空集合分支必须各有用例。
5. 覆盖率门禁只作下限：核心模块行覆盖率要求 ≥80%，但门禁通过不等于行为被守住。

## 与本仓库门禁的关系

JaCoCo 门禁有一类静默失效：`element=PACKAGE` 配合 `包名.*` 时，模式里的 `.` 被当作正则「任意字符」，`*` 被展开成 `.*`，结果匹配到的是子包而不是目标包，空集合一律判通过。改动覆盖率配置后必须用反证确认门禁真的会红（见 `ops/verify-coverage-gates.sh`）。
